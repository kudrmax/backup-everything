# Backup Everything — дизайн

Дата: 2026-09-30. Статус: на ревью.

## 1. Цель

Личное macOS-приложение, которое в одном месте знает про все бэкапы Макса: что, откуда, куда, когда делалось в последний раз и что просрочено. Работает в фоне, почти не потребляет ресурсов, автоматизирует то, что можно автоматизировать, а для остального хранит инструкцию и напоминает.

Критерии успеха:

- Новый источник или назначение добавляется через UI, без правки кода.
- Один взгляд на menu bar отвечает на вопрос «всё ли в порядке с бэкапами».
- Приложение в простое не нагружает систему: нет опроса диска, нет постоянных таймеров.
- Бэкап либо записан целиком, либо не существует. Последняя успешная копия не теряется никогда.
- Все данные приложения лежат в одной читаемой папке, которая бэкапится как обычный источник.

## 2. Что сказал Макс и что решено

Сказано Максом:

- Источники: парольник (сейчас Bitwarden, позже «Пароли» macOS), iOS-приложение финансов (CSV), Google Photos, Obsidian, GitHub (все репозитории или список), Claude.
- Назначения: внешний HDD, папка на диске, облако.
- Иконка в menu bar и полноценное окно.
- Хранение версий с увеличивающимися интервалами (GFS).
- Для ручных экспортов: оригинал после подхвата удалять или оставлять — настройка на источник, по умолчанию удалять.
- Облако через rclone сразу в MVP.
- Шифрования в MVP нет, добавится позже.
- В MVP для неавтоматизируемых источников достаточно инструкции, заданной при создании источника.
- Экспорт Claude отдаёт не архив, а манифест со ссылками на архивы. Для таких источников нужен полуавтоматический тип: последовательность шагов, где одни делает человек, а другие — команда в терминале. В копию Claude попадают только архивы, манифест не нужен.
- Файлы в «Загрузках» узнаются по именам. Переименование загрузок в браузере (Arc) Макс отключает.

Решено при проектировании:

- Стек: Swift + SwiftUI, один процесс, macOS 14+.
- Источник — это список шагов (папка, команда, файл от человека, подключить устройство); типов источника нет. Два типа назначений. Этого хватает на весь список и на комбинации вроде «подключить устройство → команда → папка».
- Шаблоны источников лежат файлами и добавляются без кода.
- Интерфейс, уведомления, сообщения и встроенные шаблоны — на английском; даты в формате en_GB (24-часовой).

## 3. Границы MVP

Входит:

- Источники из шагов четырёх видов: “Copy folder”, “Run command”, “Get a file from you”, “Connect device”.
- Назначения типов “Folder or disk” (в том числе внешний диск) и “Cloud (rclone)”.
- Расписание на источник, хранение по GFS с превью, догон недоступных назначений.
- Menu bar, окно с разделами “Overview”, “Sources”, “Destinations”, “History”, “Settings”.
- Уведомления, автозапуск при входе.
- Шаблоны источников: GitHub, Obsidian, Bitwarden, Google Photos, Claude, Claude Code, Passwords (Apple), Contacts (Apple), Finance (iOS).
- Источник “Backup Everything settings”, создаваемый при первом запуске.

Не входит:

- Шифрование.
- Мастер восстановления (есть только “Show in Finder” и «Открыть в облаке»).
- Дедупликация в облаке: туда каждый снапшот пишется целиком.
- Автоматический запуск ручных экспортов (Takeout и подобных).
- Настройка rclone remote из UI: в MVP remote создаётся в терминале по инструкции.

## 4. Модель предметной области

**Источник (Source)** — запись в конфиге:

- `id`, `name`, `steps` — список шагов, от одного и больше (4.1);
- `slug` — имя папки копий источника в назначениях (4.3). Выводится из имени при первом сохранении и больше не меняется, в том числе при переименовании. Имена папок удалённых источников запоминаются в `config.json` (`retiredSlugs`) и новым источникам не выдаются: источник с именем удалённого получает папку `photos-2`, а копии удалённого остаются нетронутыми в `photos`;
- `schedule`: `daily | weekly | monthly | manual` (только по кнопке);
- `retention`: `{daily, weekly, monthly, yearly}`;
- `destinationIds`: список назначений;
- `description`: одна-две фразы о том, что именно бэкапится (показывается под именем источника и при наведении на имя в обзоре);
- `instructions`: шаги, которые должен сделать человек (установка, вход, ручной экспорт), в Markdown; показывается в UI и в уведомлениях. Описание и инструкция — разные поля, шаблон задаёт оба;
- `icon`: необязательный значок — имя PNG-файла в `icons/`. Любой значок источника (свой или системный) рисуется на полупрозрачной серой плитке со скруглением, чтобы ряд был ровным. Любая выбранная картинка приводится к PNG 128×128; файлы, на которые не ссылается ни один источник, уходят в Корзину — только после того, как настройки прочитаны или успешно записаны, и по ним; если `config.json` не читается, значки не трогаются;
- `enabled`.

**Назначение (Destination)**: `id`, `name`, `type`, параметры типа, `expectedEvery` — как часто назначение обязано быть доступным: `always` (по умолчанию для облака и папки на внутреннем диске) или интервал «не реже чем раз в N дней» (для внешнего диска, например 30).

**Снапшот (Snapshot)** — одна версия одного источника в одном назначении. Идентифицируется временем сбора данных.

**Прогон (Run)** — одна попытка забэкапить источник: время, результат по каждому назначению, текст ошибки, размер.

**Долг (Debt)** — пара «источник, назначение», для которой бэкап не доставлен, потому что назначение было недоступно или запись упала.

### 4.1. Шаги источника

Типов источника нет. У источника есть расписание, назначения, хранение и список шагов, которые выполняются по очереди. Видов шагов четыре:

| Шаг | Кто делает | Параметры | Что даёт копии |
|---|---|---|---|
| Copy folder | приложение | `path` (папка или файл), `excludes` (glob) | содержимое папки |
| Run command | приложение | `command`, `timeoutSeconds` | то, что команда положила в `BACKUP_OUTPUT_DIR` |
| Get a file from you | человек, приложение ждёт | `instructions`, `watchPath`, `filePattern` (glob), `fileMode` (`single` или `multiple`), `includeInCopy`, `removeOriginal` | файлы, если `includeInCopy`; иначе они лежат в `BACKUP_INPUT_DIR` для следующих команд |
| Connect device | человек, приложение ждёт | `instructions`, `path` | ничего: шаг ждёт, пока путь появится (устройство подключено) |

**Что попадает в копию.** Источник из одного шага “Copy folder” отдаёт папку как есть, без промежуточной копии. Если `path` — символическая ссылка, берётся то, на что она указывает (у одного файла — под именем ссылки); ссылки внутри папки копируются как ссылки. Папка внутри, которую приложение не может прочитать (права, защита macOS), — ошибка сбора: копия без её содержимого выглядела бы полной. Исключённые папки не читаются вовсе. Шаг “Copy folder” в источнике из нескольких шагов копирует так же, как запись в локальное назначение: имена байт в байт, ссылки ссылками, даты, права, замки и расширенные атрибуты у файлов и папок. В остальных случаях шаги работают в рабочих папках запуска (`BACKUP_INPUT_DIR`, `BACKUP_OUTPUT_DIR`, `BACKUP_SCRATCH_DIR`, общие для всех шагов), и копией становится `BACKUP_OUTPUT_DIR`. Пустой результат — ошибка, снапшот не создаётся.

**Источник без шагов человека** (только папки и команды) запускается по расписанию или кнопкой “Run” и при каждом запуске, включая догон, собирает копию заново.

**Источник с шагом человека** (файл или устройство):

- Шаг человека в начале источника ждёт, только когда источник его ждёт: подошёл срок по расписанию (то же, что автоматическое нажатие “Run”) или нажата “Run”. Пока источник не ждёт, приложение папки и устройства не трогает. У источника “Manual only” ожидание включается только кнопкой. Шаг человека после автоматических шагов ждёт сам: запуск уже идёт.
- Пока ждёт шаг, начатый сроком, источник жёлтый: “time to export” (файл) или “time to connect” (устройство), и раз в сутки приходит напоминание. Начатый кнопкой — спокойное “waiting for a file” / “waiting for the device” без напоминаний; такое ожидание можно отменить кнопкой “Cancel: stop waiting” (собранное в запуске уходит в Корзину). Ожидание по сроку не отменяется: это напоминание, оно держится до бэкапа.
- Положение запуска хранится в `state.json` (`chain`: номер и `id` шага, кто начал) и переживает перезапуск приложения; прерванная команда запускается заново с начала своего шага. Повтор начинается с чистого места: вместе с положением запоминается, что лежало в `BACKUP_OUTPUT_DIR`, когда шаг начался (`outputAtStepEntry`), и всё, что прерванная попытка успела туда добавить, перед повтором уходит в Корзину; если убрать не удалось — ошибка шага. Так же упавший автоматический шаг сразу отправляет в Корзину всё, что успел добавить в `BACKUP_OUTPUT_DIR` (а не удаляет: команда могла перенести туда оригиналы); если это не удалось, шаг заканчивается ошибкой, а недоубранное не считается тем, что лежало в начале шага, — повтор снова попробует его убрать. Положение, сохранённое прежней версией приложения, этого списка не знает, и тогда ничего не убирается. Если шаги отредактировали так, что на текущем месте оказался другой шаг, запуск начинается заново, собранное уходит в Корзину.
- Результат последнего шага переносится в `pending` и доставляется оттуда: долг каждому назначению записывается до начала доставки, догон идёт из `pending`, пакет уходит из `pending` после доставки во все назначения (в Корзину, если его составляют забранные у человека файлы с `removeOriginal`, иначе удаляется). Ошибка при этом не теряется: она дописывается к результату доставки (“Could not clear the work folder: …”). Устройство поэтому читается один раз, и догон на отключённый ранее диск не требует подключать устройство снова.
- Если в источнике есть шаг “Connect device”, сразу после того как результат лёг в `pending` (до доставки в назначения), приходит уведомление “Safe to disconnect”.
- “Back up everything again” запускает источник с шагом человека, только если его первый шаг не придётся ждать: папка, команда или уже подключённое устройство. Ожидание файла не включает.

**Шаг “Get a file from you”:**

- Файлы с расширениями незавершённой загрузки (`.crdownload`, `.download`, `.part`, `.tmp`) и пустые файлы не подхватываются. Пока в папке есть любая незавершённая загрузка или подходящий файл менялся меньше 5 секунд назад, подхват откладывается. Браузеры называют недокачанные файлы по-разному, поэтому сопоставления по имени нет.
- Первый шаг берёт файлы новее последнего подхвата этого источника (или его создания) — в том числе скачанные до нажатия кнопки. Шаг в середине — файлы, появившиеся после предыдущего шага.
- `fileMode = single`: как только файл полностью скачан, он забирается сам. `fileMode = multiple` (многотомный Takeout): найденное показывается — “N files · size” с кнопкой “Pick up” — и забирается по кнопке (или “Retry step”). Кнопка недоступна, пока идёт загрузка; после неудачного подхвата она остаётся рядом с ошибкой.
- Подхват атомарный: если хотя бы один файл забрать не удалось, все остаются на месте, шаг получает ошибку “Could not pick up the files”.
- `removeOriginal = true` (по умолчанию): файл перемещается; иначе копируется, а оригинал остаётся. Тот же файл второй раз не забирается.
- Если файл найден, но в папке есть незавершённая загрузка, источник показывает “N files · size · downloading”.
- Маски разных источников на одной папке не должны пересекаться. Пересекаются маски, под которые подходит хотя бы одно общее имя файла (`*.vcf` и `Work*` — оба берут `Work.vcf`); проверяется весь синтаксис масок (`*`, `?`, `[a-z]`, `[!…]`, `\`), регистр не важен. Папки сравниваются без учёта регистра и формы Unicode, `~/Downloads`, `~/downloads/` и путь через `..` — одна папка. Шаблон без известного имени файла поставляется с пустой маской: пока она не задана, ничего не подхватывается.

**Шаг “Connect device”:** ждёт, пока путь существует (том смонтирован). Отсутствие устройства — не ошибка. Если автоматический шаг после устройства упал, а устройства уже нет (его отключили посреди копирования), запуск возвращается к шагу устройства и снова ждёт его, без ошибки. Подключение устройства (монтирование тома) само запускает проверку, поэтому следующие шаги идут без нажатий. Если путь не задан, берётся папка следующего шага “Copy folder”. Всё, что попытка, прерванная отключением, успела скопировать, перед ожиданием уходит в Корзину; если не удалось — ошибка шага (см. повтор с чистого места выше), и устройство не ждётся, пока остатки не убраны.

**Шаг “Run command”:**

- Запускается через `/bin/zsh -lc`. Ненулевой код возврата, таймаут или пустой результат — ошибка. Хвост stdout и stderr (последние 4 КБ) сохраняется в историю; байты, которые не являются UTF-8, заменяются на «�», а не обнуляют весь вывод. Команда работает в своей группе процессов. По таймауту, при отмене задачи и при выходе из приложения останавливается команда вместе со всеми порождёнными ею процессами: сначала просьба завершиться (SIGTERM), затем, если не помогло, принудительно (SIGKILL; при таймауте и отмене — через 5 секунд, при выходе — через секунду). Команда шага цепочки записывается в `chains/<sourceId>/process.json` (pid и время запуска процесса); если приложение упало или было убито, а команда осталась работать, следующий запуск шага и “Start over” сначала останавливают её группу — только если это всё ещё тот же процесс (совпадает время запуска), иначе запись просто забывается. Последняя непустая строка stdout показывается как ход работы.
- Таймаут в форме задаётся в минутах. Таймаут не кратный минуте (например, 90 секунд из `config.json`) показывается целым числом минут (округление вниз, но не меньше одной минуты) и сохраняется как был, пока число минут не изменено.
- Конфиг не хранит секретов. Командам, которым нужен токен или пароль, следует читать его из Keychain (`security find-generic-password`) или пользоваться собственной авторизацией инструмента (`gh auth`, `bw login`). Шаблоны так и написаны.

**Ошибка шага.** Упавший автоматический шаг убирает за собой всё, что успел добавить в копию, поэтому повтор начинается с чистого места. Источник без шагов человека повторяется через час (5.1). В источнике с шагом человека упавший шаг тоже повторяется сам через час — кроме команды, перед которой в этом источнике был шаг человека: она могла израсходовать то, что человек подготовил (одноразовые ссылки), поэтому ждёт “Retry step” или “Start over” (“Start over” сбрасывает запуск и сразу ждёт первый шаг). Ошибка источника из нескольких шагов называет шаг: “Step 2 of 3 “Download archives”. …”.

**Старые конфиги.** До перехода на шаги у источника было поле `kind` одного из пяти типов. Такой источник читается и превращается в шаги: «Папка» → [папка], «Команда» → [команда], «Ручной экспорт» → [файл от тебя] (общая инструкция источника переезжает в шаг), «По шагам» → те же шаги (старый ручной шаг — файл, один, `removeOriginal`), «Подключаемое устройство» → [подключить устройство, папка]. `id`, `slug`, назначения не меняются; `id` новых шагов выводятся из `id` источника и одинаковы при каждом чтении. Формат `config.json` — `schemaVersion` 2; перед первой записью в новом формате прежний файл сохраняется рядом как `config.v1.json`. Старые файлы шаблонов тоже читаются.

Шаблон Claude:

1. Шаг “Get a file from you” “Request export”: claude.ai → Settings → Privacy → Export data; по ссылке из письма скачать манифест в «Загрузки». Маска `manifest-*.json`, в копию не входит.
2. Команда “Download archives”, таймаут 60 минут. Читает из манифеста список `data_files`. Для каждого архива: если файл с именем `filename` уже лежит в «Загрузках» и изменён позже `created_at` манифеста, он считается скачанным; иначе ссылка `export_url` открывается в браузере по умолчанию в фоне (`open -g`). Если в «Загрузках» лежит одноимённый файл старше манифеста, шаг сразу завершается ошибкой с просьбой убрать его и ни одной ссылки не открывает: иначе браузер сохранил бы новый архив под именем «… (1).zip» и шаг ждал бы его до таймаута. Файл, рядом с которым лежит `.part`, считается ещё скачивающимся. Затем команда ждёт появления архивов в «Загрузках», печатая “downloaded N of M” при каждом изменении, и переносит каждый архив в `BACKUP_OUTPUT_DIR`, как только он скачан. Архив, уже лежащий в `BACKUP_OUTPUT_DIR`, считается готовым — повтор шага его ссылку не открывает. Незавершённой считается загрузка, рядом с которой лежит файл с тем же именем и расширением `.part` (Firefox), `.crdownload` (Chrome, Arc) или `.download` (Safari): такой архив не считается ни скачанным, ни старым, и его ссылка повторно не открывается. Если дождаться не удалось — ошибка со списком недостающих архивов: для недокачанных она советует дождаться загрузки или удалить прерванные файлы и повторить шаг, для остальных — запросить экспорт заново.

Ссылки экспорта одноразовые и защищены проверкой Cloudflare: без браузера (`curl`) они не скачиваются, поэтому скачивает именно браузер, в котором выполнен вход в claude.ai. После шага в браузере остаётся по вкладке на архив. Повтор шага открывает только ссылки недостающих архивов; сгоревшая ссылка лечится новым экспортом — новый манифест перезапускает цепочку.

### 4.2. Типы назначений

| Тип | Параметры | Доступность |
|---|---|---|
| Локальная папка | `path` | Путь существует и доступен на запись. Для внешнего диска это означает, что том смонтирован: путь внутри `/Volumes/<Имя>` доступен, только пока там смонтирован том. Обычная папка с тем же именем, оставшаяся на системном диске после неаккуратного отключения, — «недоступно», иначе копии молча писались бы на системный диск. Ссылка в `/Volumes` (“Macintosh HD” указывает на системный диск) считается томом. Проверяется то место, куда путь ведёт на самом деле: путь сначала раскрывается (ссылки по дороге, `..`), и папка внутри `/Volumes` узнаётся и под другим написанием (`/System/Volumes/Data/Volumes/…`, другой регистр букв), и через ссылку снаружи. |
| Rclone | `remote`, `path` | `rclone lsf remote:` завершился успешно за 15 секунд. Проверяется корень remote: папка бэкапов в облаке может ещё не существовать. |

Rclone:

- Используется установленный в системе `rclone` (поиск в `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin`). Если его нет, раздел “Destinations” показывает инструкцию по установке.
- Используется стандартный конфиг rclone (`~/.config/rclone/rclone.conf`). Токены облаков остаются там и не попадают в папку приложения. Создание remote — по инструкции в UI через `rclone config` в терминале.
- В облако уходят только обычные файлы: символические ссылки и пустые папки не переносятся. В локальное назначение копируется всё.

### 4.3. Раскладка снапшотов

```
<корень назначения>/<slug источника>/<YYYY-MM-DD_HHmmss>/   (в повторяющийся час перевода часов — <YYYY-MM-DD_HHmmss±HHMM>)
    …содержимое…
    _unfinished         ← метка «пишется», кладётся первой и убирается после манифеста
    _snapshot.json      ← манифест, пишется последним
```

- Имя папки снапшота — местное время сбора. Когда часы переводят назад, час повторяется; снапшоты этого часа получают в имени смещение от UTC (`2026-10-25_023000+0200` до перевода, `2026-10-25_023000+0100` после), поэтому два бэкапа с разницей в час не получают одно имя и каждый читается как свой момент. Снапшоты, записанные в этот час прежними версиями (без смещения), остаются снапшотами.
- `slug` — имя одной папки. Если в `config.json` (например, правкой руками) оказался пустой `slug` или со `/` или `..`, назначение (локальное и облачное) отказывается что-либо читать, писать и удалять для этого источника: ошибка “The folder for copies of this source is named “…”, which is not a single folder name. Nothing was read, written or deleted. Fix “slug” of the source in config.json.”. Корень назначения и чужие папки так никогда не трогаются.
- Снапшот источника — папка в папке его `slug`, манифест которой называет `id` этого источника (или не читается). Снапшот, манифест которого называет другой источник (так бывает в настройках, сделанных до запоминания имён папок удалённых источников), этому источнику не принадлежит: чистка по GFS его не удаляет и не учитывает, догон не берёт его как готовую копию, а копия с тем же именем не считается уже доставленной — запись упирается в чужую папку (см. ниже).
- Манифест содержит id и имя источника, время сбора, количество файлов, суммарный размер. У локального назначения в нём ещё список файлов копии (путь, размер, SHA-256, время изменения) и признак `sharesData` — делит ли копия данные с прошлыми (4.3.1).
- Снапшот считается существующим только при наличии манифеста. Недописанный снапшот — папка, которую приложение начало и не дописало: в ней есть метка `_unfinished` и нет манифеста. Такие папки этого источника убираются только после того, как в это же назначение успешно записан новый снапшот (или он там уже был): в локальном назначении — в Корзину, в облаке (Корзины нет) — удаляются. Папка без манифеста и без метки (например, снапшот, у которого пропал манифест, или старые недописанные папки, записанные до появления метки) снапшотом не считается и не трогается никогда.
- Если при записи на месте нового снапшота уже лежит недописанная папка с тем же именем (повтор той же копии), она убирается (в локальном назначении — в Корзину, в облаке — удаляется) и снапшот пишется заново, без остатков прошлой попытки; если там любая другая папка (без метки или чужой готовый снапшот), запись не идёт, папка не трогается, а в ошибке назван путь мешающей папки. Так работают оба типа назначений.
- Эта схема одинакова для локальной папки и rclone и не требует атомарного переименования на стороне облака.
- Файлы лежат как есть, без архивации и без проприетарного формата: снапшот открывается в Finder или в веб-интерфейсе облака без приложения.
- В локальном назначении имена файлов и папок внутри снапшота совпадают с оригиналом байт в байт: форма Unicode не меняется (например, «й» не раскладывается на «и» и знак краткости).
- В локальном назначении у файлов и папок снапшота даты, права, замок Finder (“Locked”) и расширенные атрибуты (теги, метки) — как у оригинала. Папки получают их после своего содержимого, начиная с самых глубоких: папка только для чтения всё равно заполняется, а дата папки не сдвигается от записи в неё.
- Файлы, которые APFS хранит сжатыми (флаг `UF_COMPRESSED`, данные в атрибуте `com.apple.decmpfs` и resource fork), копируются сжатыми и в копии читаются целиком. Сжатие — способ хранения, а не свойство, видимое человеку: его флаг и эти атрибуты никогда не переносятся с другого файла и не снимаются, иначе файл становится пустым.
- Каждый записанный файл проверяется: его размер (как его видят читатели, для сжатого — после распаковки) равен размеру оригинала. Если не равен, а оригинал за время копирования не менялся, запись снапшота падает с ошибкой “The copy of “…” came out N bytes long instead of M. …”; если оригинал менялся (живой файл), в копии остаётся прочитанное, и манифест описывает его.
- Файл или папка, исчезнувшие после того, как их папку прочитали (живые папки, кэши), в снапшот не попадают и ошибкой не считаются; от исчезнувшей папки может остаться пустая. Файл, который есть, но не читается, — по-прежнему ошибка.
- Имена `_snapshot.json` и `_unfinished` на верхнем уровне снапшота принадлежат приложению. Если у источника на верхнем уровне лежит файл или папка с таким именем (без учёта регистра и формы Unicode), сбор заканчивается ошибкой “… has the name Backup Everything gives its own file in every copy. Rename it, move it into a subfolder or add it to the exclusions.”, снапшот не начинается: иначе недописанная копия с чужим `_snapshot.json` считалась бы готовой. Глубже такие имена — обычные файлы: они копируются, в том числе при догоне.
- Локальный снапшот удаляется так: сначала с самой папки снимается замок, и она переименовывается в `<имя>.deleting`, затем удаляется целиком — с каждого элемента снимаются замок и списки доступа, папки открываются владельцу. Если удаление прервалось, остаток уже не похож на снапшот (имя не читается как дата) и дочищается после следующей успешной записи в это назначение. Других папок с суффиксом `.deleting` приложение не трогает.

### 4.3.1. Неизменившиеся файлы в локальном назначении

У источника есть выключатель “Save space” (`savesSpace`, по умолчанию включён, в том числе у источников из старых настроек). Включён — неизменившееся не записывается заново, как описано ниже; выключен — каждый снапшот пишется целиком.

Каждый снапшот — полная папка, но содержимое, которое уже лежит в одном из прошлых снапшотов этого источника в этом же назначении, не записывается заново: файл становится APFS-клоном. Клон — отдельный файл с общими данными на диске, поэтому правка файла в одном снапшоте не меняет другие, а удаление снапшота не трогает остальные. Восстановление — скопировать папку нужного снапшота, ничего собирать не нужно.

- Совпадение определяется по SHA-256 содержимого, а не по имени и дате: переименованный, перемещённый и вернувшийся после удаления файл тоже клонируется. Ищется во всех снапшотах источника с манифестом нового вида, самые свежие первыми; одинаковые файлы внутри одного снапшота тоже хранятся один раз.
- Файл-оригинал используется, только если с записи его размер и время изменения не менялись, а его настоящий размер равен размеру файла источника; файл, который правили руками, не служит оригиналом. Так копии, испорченные прежней версией (сжатые файлы в них стали пустыми, а манифест записал размер 0 с хэшем источника), не размножаются: такой файл пишется заново целиком.
- Хэш нового файла считается по записанной копии, а не по оригиналу: если оригинал менялся во время копирования, манифест всё равно описывает то, что лежит в снапшоте. Хэш файла источника считается заранее, только если в прошлых снапшотах есть файл того же размера.
- У клона то, что человек видит у файла источника: даты создания, изменения и доступа, права доступа, флаги “Locked”, “append only”, “hidden”, “nodump”, “opaque”, список доступа и расширенные атрибуты (теги, метки, карантин) — как у файла источника; от файла, с которого сделан клон, не остаётся ничего, кроме данных. Данные клона при этом не трогаются: его сжатие (флаг `UF_COMPRESSED`, атрибут `com.apple.decmpfs` и resource fork) остаётся как есть, сжатие файла источника клону не передаётся. Атрибут `com.apple.provenance` ведёт система, он не переносится и не снимается. Если у файла источника есть свой resource fork, а клон сжат (fork занят его данными), клон не делается, файл копируется. Клон, который после этого не совпал по размеру с файлом источника, удаляется, и файл копируется.
- Если том назначения не поддерживает клоны (не APFS), снапшот пишется целиком, как раньше, со списком файлов и `sharesData = false`. Сбой клонирования конкретного файла — не ошибка: недоделанный клон удаляется, файл копируется. Если недоделанный клон не удаётся удалить, запись снапшота падает с этой ошибкой.
- Снапшоты, записанные до появления клонов (без списка файлов), оригиналами не служат: первый снапшот после обновления пишется целиком.
- Выключатель неактивен (выключен и без руки-курсора), если ни одно выбранное назначение не позволяет клоны: облако, диск не APFS, или назначения не выбраны. Если позволяют не все, рядом подпись “full copies in “Cloud”” — там снапшоты всё равно пишутся целиком; если ни одно — “not possible in …”. Подсказка у названия объясняет, что это и где работает. Что позволяет отключённый диск, приложение помнит с последнего подключения (проверяется вместе с занятым местом); диск, который ещё ни разу не был подключён, считается позволяющим — проверка будет при записи.
- «Сколько занимают копии» у локального назначения — одно число: сколько места реально занято на диске. Обходятся все файлы папки назначения, у каждого берётся занятое место из файловой системы; данные, общие у клонов, считаются один раз (APFS сообщает у файла номер группы клонов и сколько байт принадлежит только ему). От манифестов подсчёт не зависит. На диске не APFS — просто сумма занятого места файлов.

### 4.4. Хранение (GFS)

Правило на источник: «последняя копия за каждый из N последних дней с копиями, одна в неделю за последние M недель, одна в месяц за последние K месяцев, одна в год за последние Y лет». Несколько копий за один день сворачиваются в самую свежую. Значения по умолчанию: 7 / 4 / 12 / 0.

Алгоритм (семантика restic и borg):

```
keep(snapshots, rules):
  sorted = snapshots по убыванию времени
  keepSet = { sorted[0] }                 // последняя копия живёт всегда
  для каждого уровня (day, week, month, year) с n > 0:
    seen = []
    для s в sorted:
      b = корзина(уровень, s.date)        // день | ISO-неделя | месяц | год, локальный календарь
      если b уже в seen: пропустить
      если len(seen) == n: стоп
      seen.append(b); keepSet.add(s)
  удалить snapshots \ keepSet
```

- Считаются только непустые корзины: пропущенные дни не съедают квоту.
- Применяется отдельно для каждой пары «источник, назначение» и только после успешной записи нового снапшота. Учитываются и удаляются только снапшоты самого источника (4.3): копии другого источника в той же папке не занимают корзины и не удаляются.
- Форма источника показывает превью: какие из существующих снапшотов останутся и какие удалятся при текущих числах.

## 5. Поведение

### 5.1. Расписание

- Источник пора бэкапить, когда `последний плановый прогон + интервал ≤ сейчас`. Источник, который ещё ни разу не запускался, пора бэкапить сразу.
- После неудачного сбора данных или неудачной записи повтор идёт не раньше чем через час — и для плановых прогонов, и для догона. Исключение — упавшая команда после шага человека: она не повторяется сама (см. 4.1).
- Планировщик держит один таймер до ближайшего срока и пересчитывает его после каждого прогона, изменения конфига, пробуждения Mac и монтирования тома. Периодического опроса нет.
- Если Mac спал в момент срока, прогон стартует после пробуждения.
- Прогоны выполняются строго по одному.

### 5.2. Один прогон

1. Источник собирает данные (папка, результат команды, подхваченный пакет или результат цепочки шагов).
2. Для каждого назначения источника:
   - доступно — записать снапшот (метка, файлы, манифест, снятие метки), затем убрать недописанные папки, применить GFS; ошибка этой чистки — предупреждение, а не провал доставки. Если не удалось убрать недописанные папки или получить список снапшотов, GFS не применяется. Снапшот, который не удалось удалить, не мешает удалить остальные: удаляются все, какие получится, а в предупреждении перечислены ошибки;
   - недоступно или запись упала — записать долг.
3. Записать прогон в историю, обновить статус, при ошибке показать уведомление.

Сбой в одном назначении не влияет на остальные.

### 5.3. Долги и догон

- При монтировании тома, пробуждении и перед каждым плановым прогоном планировщик проверяет долги.
- Источник собирается один раз за запуск; назначение, которое запуск пропустило (было отключено, упало или добавлено позже), получает уже сделанную копию. Порядок выбора, как только должник доступен: пакет из `pending` (у источников с шагом человека); иначе самая свежая копия источника (4.3: не чужая копия в той же папке) на другом доступном его назначении — переносится как есть, под тем же именем, источник заново не собирается (GitHub ничего не качает, устройство подключать не нужно; при равной дате берётся локальное назначение, облако скачивается во временную папку); иначе, если готовой копии нет нигде, источник без шагов человека собирается заново, а источник с шагом человека остаётся должен до своего следующего бэкапа (поиск копии повторяется раз в час, значок назначения в строке — “waiting to be connected”). Пакет удаляется из `pending`, когда доставлен во все назначения.
- После догона на внешний диск приходит уведомление “Safe to disconnect the disk”.
- Назначение с интервалом `expectedEvery` (“Can stay unplugged” · “up to N days”) не обязано быть подключено постоянно. Каждый долг помнит, есть ли пропущенный бэкап на другом назначении источника (`elsewhere`: запуск доставил его куда-то ещё; для пропавшей копии — у источника есть копия на другом назначении; если хоть один пропущенный бэкап нигде больше нет, флаг снимается до закрытия долга). Если какого-то пропущенного бэкапа больше нигде нет (например, диск — единственное назначение источника), напоминание приходит сразу. Иначе, пока с последнего успешного догона прошло меньше интервала, долги не влияют на статус и не вызывают напоминаний; когда интервал вышел — напоминание. Оно повторяется раз в сутки. Текст: “Connect “HDD”” + “The backup of “X” exists nowhere else. It will be written as soon as you connect the disk.” или “The disk hasn’t been connected for a while. Copies are on other disks, but this one needs updating too.”. В настройках назначения правило написано текстом под строкой срока; в подсказке значка назначения в строке источника — “a copy is on “…”” или “this backup exists nowhere else — connect the disk”; в подсказке назначения внизу обзора — что больше нигде нет или когда напомню.
- Сколько бы плановых прогонов ни было пропущено, догон создаёт один свежий снапшот на источник, а не по снапшоту за каждый пропущенный день.
- Догон готовой копией (с другого назначения или из `pending`) закрывает только проблемы доставки. Если последний сбор источника упал (ждёт повтора через час), такая старая копия не делает источник зелёным и не отменяет повтор: ошибка сбора остаётся, пока сбор не пройдёт. Догон, который собрал источник заново (готовой копии не было нигде), — это успешный сбор: он снимает ошибку.
- Долги выключенного источника ждут его включения: догон их не закрывает, поэтому они не влияют на статус, не дают напоминаний “Connect …” и не будят планировщик. Сами долги сохраняются — после включения догон и напоминания продолжаются с того же места.

### 5.3.1. Сверка с назначениями

Приложение не полагается только на собственные записи: оно проверяет, что копии действительно лежат в назначении.

- На каждом `tick()` (запуск приложения, открытие окна, пробуждение, подключение диска, плановый срок) для каждого доступного назначения проверяется, что последняя доставленная копия каждого источника на месте. Локальные назначения сверяются каждый раз, облачные — не чаще раза в сутки.
- Если копии нет, паре «источник, назначение» записывается долг, и в этом же `tick()` он закрывается по правилам догона (5.3). Приходит уведомление “Copy missing”, в “History” остаётся запись догона.
- Если источнику добавили новое назначение, копия туда делается сразу, не дожидаясь планового срока; уведомления “Copy missing” при этом нет. Поэтому после каждого сохранения настроек через пару секунд идёт `tick()`.
- Для копий, сделанных до появления сверки, последняя доставленная копия определяется по истории прогонов.
- Недоступное назначение и назначение, список копий которого не удалось получить, не сверяются: отсутствие ответа не считается пропажей. Пустой список локальное назначение отдаёт только когда папки источника в нём нет; папка, которую нельзя прочитать, — ошибка, а не «копий нет».

### 5.4. Ошибки

- Недописанный снапшот не считается снапшотом (нет манифеста). Убирается только после успешной записи нового снапшота (5.2, 4.3).
- Чистка по GFS идёт только после успешной записи нового снапшота. Снапшоты, удалённые чисткой, удаляются безвозвратно, минуя Корзину.
- Путь источника исчез, источник не дал ни одного файла или часть его не читается — ошибка; существующие снапшоты не трогаются. Файл или папка внутри источника, исчезнувшие во время обхода, — не ошибка: их просто нет в копии (4.3).
- Если корневая папка локального назначения отсутствует (диск не подключён), приложение её не создаёт и ничего не пишет по этому пути.
- В папке источника в назначении приложение удаляет только папки с именем снапшота (и их остатки `<имя>.deleting`, 4.3); посторонние файлы и папки не трогает.
- Последняя успешная копия не удаляется при любых значениях правила. Только что записанный снапшот чисткой этого же прогона не удаляется никогда.
- Источник, все назначения которого удалены, считается источником без назначений: не запускается и отмечается в статусе.
- Файл настроек, который существует, но не читается, — ошибка; пустыми настройками он не подменяется.
- Нехватка места: приложение не удаляет ничего сверх правила, помечает ошибку и уведомляет.
- Ошибки в истории и уведомлениях формулируются человеческим языком с техническими деталями под спойлером.

### 5.5. Статус в menu bar

| Статус | Условие |
|---|---|
| Спокойный | Все включённые источники свежие, долгов нет. |
| Жёлтый | Источник ждёт шага человека, а запуск начат сроком (“time to export”, “time to connect”); есть найденные файлы, ждущие “Pick up”; назначение `always` недоступно и имеет долг; у назначения с интервалом вышел срок подключения; у источника не выбрано ни одного назначения. Ожидание, начатое кнопкой (“waiting for a file”, “waiting for the device”), статус не портит. |
| Красный | Последний прогон какого-либо источника завершился ошибкой, либо источник, который уже запускался, просрочен более чем на два интервала. Источник, который ещё ни разу не запускался, красным не считается: он запустится при первой возможности. |

Значок в menu bar цветной: жёлтый — нужно действие, красный — ошибка, обычный (белый/чёрный по теме) — всё в порядке. Меню по клику, сверху вниз: “Open window”; блок состояния без общего заголовка — по одной строке на проблему: значок состояния (красный — ошибка, оранжевый — нужно действие), значок источника или назначения, имя и короткая причина (“time to export”, “2 files · 23 GB” с кнопкой “Pick up”); ошибки идут первыми; у источника одна строка, даже если проблем несколько. Если проблем нет — “All good · last backup N ago”. Клик в любое место блока открывает окно на “Overview”, даже когда действий не нужно; “Back up everything again”; “Quit”. Ошибка в меню показывается одной короткой фразой (полный текст — в окне). Во время работы первой идёт строка выполняющегося источника: “GitHub · 9 of 79 · owner/repo · 4 min”. “Launch at login” живёт в разделе окна “Settings”.

### 5.6. Окно

- **Обзор** — один компактный список, строка на источник. В строке видно только: значок состояния, название, короткая пометка (появляется, только когда что-то не так или идёт работа), давность последнего бэкапа, когда следующий (“→ in 17 h”, “→ due”, “→ manual” у источников “Manual only”, “→ waiting”, пока источник ждёт файл или устройство) и значки назначений. Точное время следующего бэкапа — при наведении и в настройках источника строкой “Next backup”. Подробности — при наведении. В шапке — “Refresh” (тот же `tick()`, что идёт сам по таймеру и событиям: докопировать недостающее и запустить то, чему пора; лишних бэкапов не делает) и “Back up everything again” (собрать всё заново и записать на все подключённые диски); то же есть в меню строки меню. Запуски доступны и во время идущего бэкапа — встают в очередь. Порядок строк выбирается в шапке: “As in settings” (порядок из “Sources”) или “By next backup” (ближайший и просроченный выше; без расписания и выключенные — внизу в порядке настроек); выбор запоминается. Кнопки строки появляются при наведении прямо в строке, пометка на это время укорачивается; обрезанная пометка целиком видна в подсказке. Источник, который ждёт своей очереди, помечен песочными часами и “queued” — в том числе сразу после “Run” или “Back up everything again”, нажатых, пока идёт другой бэкап (помечаются те, что пойдут в работу, а не будут ждать файл или устройство). Проверка, вставшая в очередь за идущим бэкапом (например, после сохранения настроек), сразу помечает то, что сделает наверняка: источники, которым пора по расписанию, и долги перед доступной локальной папкой или диском, которые есть чем закрыть и которые пора повторять. Пока идёт шаг без своего прогресса, пометка говорит, что он делает: “copying files…” или “running the command…”.
- **Подсказки и кнопки во всём приложении.** Открытая подсказка следит за своим текстом (идущее время обновляется). Подсказка к идущему бэкапу сравнивает его с прошлым таким же: копирование с другого диска — с прошлым копированием, сбор — с прошлым плановым или ручным сбором; запись пакета после шагов человека для сравнения не годится; не с чем сравнить — прогноза нет. Подсказка всплывает через полсекунды (следующая — сразу), пропускает мышь насквозь и исчезает при уходе курсора, клике, прокрутке или нажатии клавиши: курсор и клик под ней работают. Кнопка нажимается всей своей площадью, под курсором подсвечивается, при нажатии темнеет, выключенная — приглушена и без руки-курсора. Пункты меню в строке меню — строки во всю ширину с подсветкой; блок состояния в меню целиком открывает обзор.
  - Шапка: общий итог (“All good”, “Needs your action”, “N errors”), имя источника, который идёт сейчас, кнопка «запустить всё».
  - Пометка во время работы: “queued”, “preparing the copy…”, “copying to “destination name”…”. Если команда источника что-то печатает в stdout, последняя непустая строка показывается как ход работы: “preparing the copy · 54 of 79 · owner/repo” (шаблон GitHub печатает номер и имя репозитория). Вместо давности на время работы показывается, сколько уже идёт запуск; при наведении — сколько занял прошлый успешный запуск.
  - Пока источник в очереди или выполняется, его прежние проблемы (ошибка прошлого запуска, просрочка) не показываются и не считаются — ни в заголовке, ни в списке, ни в menu bar. Если других проблем нет, заголовок на это время — “Backing up”.
  - Текст ошибки в строке — кнопка: открывает окно с полным текстом (прокрутка, выделение, “Copy”). При наведении показывается только подсказка, а не сам текст. То же окно доступно из «⋯ → Показать ошибку». В “History” у запуска с ошибкой полный текст выделяется и копируется кнопкой.
  - Пометка при проблеме: начало текста ошибки (для упавшей команды — последняя непустая строка её вывода, в ней обычно причина), “N files · size” с кнопкой “Pick up”, “time to export”. Полный текст — при наведении.
  - У источника из нескольких шагов пометки о самом запуске (пора сделать экспорт, пора подключить, найденные файлы, ждёт файл, ждёт подключения, ошибка шага) начинаются с положения: “step 1 of 2 · time to export”, “step 2 of 3 · waiting for a file”, во время команды — “step 2 of 2 · downloaded 3 of 5”, при ошибке — “step 2 of 2 · <начало текста ошибки>”; остальные (“no destination chosen”, ошибка доставки) — без положения. Те же тексты — в строке меню. Кнопки при наведении описаны ниже.
  - Значок назначения — диск или облако с меткой: зелёная галочка — последняя копия источника там есть; оранжевые часы — ещё не доставлена, назначение недоступно; красный крест — запись упала; синий пульсирующий — записывается сейчас; серый без метки — копий ещё не было. При наведении — имя назначения и время доставки.
  - Давность последнего бэкапа — это возраст самой свежей копии источника, доставленной хотя бы в одно назначение, включая догон и восстановление пропавшей копии; расписание при этом отсчитывается отдельно, от последнего планового прогона. Запуск, который не доставил копию ни в одно назначение (диск отключён, запись упала), давностью не считается: у такого источника давность “—”, и “last backup …” в меню строки меню его не учитывает. Для `state.json` из старых версий без отметки о доставленной копии давность берётся из истории: самый свежий запуск, доставивший копию хотя бы в одно назначение.
  - При наведении на давность — точное время последнего и следующего бэкапа и размер копии. При наведении на строку — кнопки-значки без меню «⋯»: “Run” (у упавшего шага — “Retry step”), “Start over” (у цепочки, которая в процессе), “Instructions” (если она есть), “Show original in Finder” (у папки — открывает её в Finder), “Open copy” (самая свежая доставленная копия в Finder; при нескольких назначениях — выбор из списка, копия в облаке видна, но неактивна), “Edit”. Кнопки, которые ничего не сделают, не показываются. Клик по свободному месту строки открывает настройки источника; полный текст ошибки открывается кликом по самой пометке.
  - Внизу — строка назначений; текстом выделяется только требующее действия (“time to connect”, “unavailable”). Назначение, которое сейчас не подключено, приглушено; меток в углу значка в этой строке нет — состояние видно по цвету и тексту. Каждое назначение — кнопка: подключённую папку или диск открывает в Finder, а облако и неподключённый диск — в настройках назначения. Рядом с именем — сколько занимают копии (у отключённого диска — на момент последнего подключения; считается в фоне между бэкапами: сразу после бэкапа и как только диск подключили, а при прочих обновлениях экрана — не чаще раза в минуту). Под строкой — “Backups need about N of free space on the laptop · M free”: бэкапы идут по одному, поэтому N — самый большой из последних бэкапов включённых источников, которые собираются во временную папку (папка из одного шага копируется напрямую и не считается), плюс пакеты, которые ждут записи на отключённый диск (пакет самого большого источника — это его же последний бэкап и второй раз не считается; если размер последнего бэкапа неизвестен, пакет считается); если свободно меньше N — строка оранжевая с предупреждением. Подробности — в подсказке.
- **Источники** — два столбца в стиле обзора: слева список (значок, имя, “Add”: шаблоны и “Empty — start with”: “Folder”, “Command”, “File you export yourself”, “Folder on a connected device” — последний сразу создаёт два шага; источники переставляются перетаскиванием: брошенный встаёт на место того, на который его бросили, на “Add” — в конец; полоска показывает, куда встанет; этот порядок — порядок источников везде: в обзоре, меню и настройках), справа: шапка (значок — клик выбирает картинку, имя, выключатель, «⋯» с “Remove icon” и удалением), под ней описание, затем блоки: выделенный цветом “How often and where” (расписание, “Next backup”, назначения-чипы, выключатель “Save space” — 4.3.1), “What to do” — карточки шагов по порядку (у источника из одного шага — без номера и стрелок; вид шага, название и поля вида; “Add step”, переставить, удалить; текущий шаг запуска подсвечен), “More” (свёрнутые “Keep copies” и “Instructions: one-time setup”). “Keep copies” — четыре строки, точно описывающие правило 4.4 (считаются периоды, в которые был бэкап, а не календарное время): “Keep one copy per day for the last [7] days you backed up”, то же для week, month, year; под ними “Older copies are deleted. The newest copy is always kept.” (если все нули — “Only the newest copy is kept.”). Числа меняются прямо в строках; строка с нулём приглушена и подписана “not used”. Свёрнутая строка показывает самый длинный этап (“last 12 months you backed up”). Там же кнопка “Show copies by date…”. Значок источника показывается и в обзоре.
- **Назначения** — те же два столбца. В списке и шапке значок с меткой состояния (на связи, не подключено, пора подключить, недоступно), подробности при наведении. Карточка настроек: папка или облако (список remote из `rclone listremotes`), режим подключения, срок напоминания. Ниже “Copies”: занятое место и строки по источникам (число копий, возраст последней), раскрываются в список дат. Для локальных назначений при наведении на копию — “Show in Finder”; для облака показывается имя папки снапшота (универсальной ссылки «открыть в облаке» у rclone нет).
- Планка “Cancel / Save” появляется только при несохранённых изменениях (или при добавлении); в ней же показывается, чего не хватает для сохранения. Если записать настройки не удалось (например, `config.json` повреждён), показывается ошибка, а правки остаются несохранёнными: планка не исчезает, новый источник или назначение не считается добавленным, удаление не происходит. После сохранения редактор показывает источник таким, каким он записан (с папкой копий, выбранной по имени), поэтому “Show copies by date…” у только что добавленного источника смотрит в его папку.
- Размеры округляются до показа, и единица выбирается по округлённому числу: 999 950 байт — “1 MB”, а не “1000 KB”.
- Второй запуск приложения, пока первое работает, сразу завершается и ничего не трогает: не чистит `staging/` (там может идти бэкап первого), не создаёт настройки, не убирает значки и не открывает окно. Второй запуск определяется по другим процессам с тем же bundle id (свой процесс не в счёт), поэтому он распознаётся и при запуске бинарника напрямую, мимо LaunchServices.
- Окно запоминает последний открытый раздел и выбранный элемент. При первом запуске (нет ни одного назначения) окно открывается само, дальше приложение живёт в menu bar.
- **История** — журнал прогонов с фильтром по источнику и результату.

### 5.7. Шаблоны

Шаблон — JSON-файл с предзаполненными полями источника (шаги, расписание, хранение, описание, инструкция). Встроенные шаблоны копируются в папку данных при первом запуске. Свой шаблон добавляется файлом в эту папку.

## 6. Данные приложения

Папка данных `~/BackupEverything/` (бэкапится источником “Backup Everything settings”):

```
config.json            источники, назначения и имена папок удалённых источников (`retiredSlugs`)
state.json             последние сборы, долги, отметки подхвата, положение в цепочках шагов
history/YYYY-MM.jsonl  прогоны, одна строка — один прогон
templates/*.json       шаблоны источников
icons/*.png            значки источников
```

Рабочая папка `~/Library/Application Support/BackupEverything/` (не бэкапится):

```
pending/<sourceId>/<timestamp>/   подхваченные, но не доставленные пакеты
chains/<sourceId>/                рабочие папки цепочки шагов: input/, output/, scratch/; process.json — идущая команда шага
staging/                          временные выходные папки команд; удаляется целиком при запуске приложения
```

- Запись файлов состояния атомарная (временный файл и переименование).
- Прогон дописывается в конец `history/YYYY-MM.jsonl`. Если прошлая запись оборвалась на середине строки (приложение упало), новая начинается с новой строки: оборванная пропускается при чтении, новая не теряется.
- Рабочие папки удалённых источников (`chains/<sourceId>/`, `pending/<sourceId>/`) при следующем `tick()` уходят в Корзину.
- В рабочих папках лежат копии с замками, правами только для чтения и списками доступа «запретить удаление» оригиналов. Когда приложение убирает что-то из `pending`, `chains` или `staging`, такие препятствия снимаются (без перехода по ссылкам): элемент сначала отправляется в Корзину как есть, и только если не вышло — разблокируется целиком и отправляется снова; удаляемое безвозвратно разблокируется всегда. В назначениях копии сохраняют права оригиналов.
- Файлы версионируются полем `schemaVersion`. Поле `retiredSlugs` в `config.json` добавлено без смены версии: файл без него читается как «удалённых источников нет».
- Секретов в папке данных нет.

## 7. Архитектура

Два модуля:

- **`BackupCore`** — Swift Package без зависимостей от UI. Вся логика и все тесты.
- **`BackupEverythingApp`** — SwiftUI: `MenuBarExtra`, окно, уведомления, автозапуск (`SMAppService`). Читает наблюдаемое состояние ядра и вызывает его команды.

Приложение не в песочнице (запуск команд и доступ к произвольным папкам), распространяется локальной сборкой.

Компоненты ядра:

| Компонент | Ответственность | Зависит от |
|---|---|---|
| `SourceProvider` (протокол) и `FolderSource` (одна папка), `StepsSource` (автоматические шаги), `PendingSource` (результат из `pending`) | Собрать содержимое снапшота (`Payload`) и убрать за собой после прогона | `ProcessRunner`, `ManualExportInbox` |
| `ManualExportInbox` | Поиск файлов шага “Get a file from you”, хранение недоставленного пакета в `pending` | — |
| `StepExecutor` | Выполнить автоматический шаг (папку или команду) в рабочих папках запуска | `ProcessRunner` |
| `StepChainRunner` | Сделать один переход запуска источника с шагом человека: принять файл, дождаться устройства, выполнить автоматический шаг или собрать результат в `pending`. `BackupCoordinator` вызывает его в цикле и сохраняет состояние после каждого перехода | `ManualExportInbox`, `StepExecutor` |
| `DestinationStore` (протокол) и `LocalFolderDestination`, `RcloneDestination` | `isAvailable`, `write(payload)`, `listSnapshots`, `removeIncomplete`, `delete(snapshot)`, `usedBytes` | `ProcessRunner` |
| `PayloadWalker`, `PayloadCopier` | Список содержимого `Payload` (ошибка на нечитаемом) и его точная копия в папку: шаг “Copy folder” и запись локального снапшота | — |
| `SnapshotWriter`, `StoredContentIndex`, `FileCloning` (`APFSCloning`), `DestinationUsage` | Запись локального снапшота с клонами неизменившегося содержимого и учёт занятого места (4.3.1) | — |
| `FolderRemoval`, `VolumeMounts` | Удаление снапшота вместе с замками, правами и списками доступа; проверка, что том в `/Volumes` смонтирован | — |
| `RetentionPolicy` | Чистая функция: список снапшотов и правило → что оставить | — |
| `BackupEngine` | Один прогон: сбор, доставка, чистка; возвращает запись прогона | провайдеры, `RetentionPolicy` |
| `StateReducer` | Применить запись прогона к состоянию: долги, сроки, ошибки | — |
| `SchedulePlanner` | Чистые расчёты: что пора запускать, какие долги повторять, когда проснуться | — |
| `BackupCoordinator` (actor) | `tick()`: догон, подхват, плановые прогоны, напоминания; строго по одному | всё перечисленное, `TimeSource` |
| `FolderWatcher` | События файловой системы для папок шагов “Get a file from you” (FSEvents) | — |
| `Store` | Чтение и атомарная запись `config`, `state`, `history`, `templates` | — |
| `StatusReporter`, `ReminderPlanner` | Сводный статус для UI и напоминания раз в сутки | `SchedulePlanner` |

Новые виды шагов добавляются в `StepKind`, `StepExecutor`/`StepChainRunner` и форму шага; новые типы назначений — реализацией протокола и регистрацией в фабрике; остальной код о конкретных типах не знает. Шифрование позже добавляется как обёртка над `DestinationStore` (или через rclone crypt) без изменений движка.

Запуск процессов и время спрятаны за протоколами `ProcessRunner` и `TimeSource`. Файловые операции не абстрагируются: тесты работают с настоящими временными папками, это надёжнее поддельной файловой системы. Состояние с конкурентным доступом изолировано актором `BackupCoordinator`.

Реализация идёт двумя планами. Первый — `BackupCore` целиком, без системных событий. Второй — приложение: таймер до ближайшего срока, события пробуждения и монтирования, `FolderWatcher`, уведомления, автозапуск и UI; все они вызывают `BackupCoordinator.tick()`.

## 8. Тестирование

Разработка через TDD.

- `RetentionPolicy` — табличные тесты: пропуски, границы недель и месяцев, нулевые правила, единственный снапшот.
- `BackupEngine` — тесты на фейковых провайдерах: успех, сбой одного назначения, недоступное назначение и долг, догон, порядок «запись, затем чистка недописанных, затем GFS», без чистки при упавшей записи.
- Недописанные снапшоты — в Корзину уходят только папки с меткой `_unfinished` и без манифеста; папка без метки и посторонние папки не трогаются; повтор под тем же именем; мешающая чужая папка — для локальной папки и облака.
- Имена снапшотов при переводе часов, принадлежность копий источнику по манифесту, имена папок удалённых источников, пересечение масок.
- `SchedulePlanner` и `BackupCoordinator` — тесты с управляемым временем: срок, повтор через час, догон при возврате диска, одновременные `tick()`.
- `ManualExportSource` — автоподхват в режиме `single`, подхват по подтверждению в режиме `multiple`, незавершённые загрузки, старые файлы, замена пакета в `pending`.
- Долги и `expectedEvery` — статус и напоминания до и после истечения интервала, один снапшот при догоне.
- `CommandSource` — код возврата, таймаут, пустой результат (фейковый `ProcessRunner`).
- `StepChainRunner` и цепочки в `BackupCoordinator` — ручной шаг ждёт и принимает файл, `includeInCopy`, передача файлов команде, остановка на ошибке без автоповтора, “Retry step”, “Start over”, перезапуск новым файлом первого шага, продолжение после перезапуска приложения (повтор прерванного шага с чистого места, остановка оставшейся от прошлого запуска команды), доставка и догон через `pending`.
- Команда шаблона Claude — на временной папке вместо «Загрузок» и с подменой `open`: уже скачанные архивы не открываются повторно, устаревший одноимённый файл останавливает шаг до открытия ссылок, недостающие перечислены в ошибке.
- `Store` — атомарность записи, чтение повреждённого файла, миграция `schemaVersion`.
- Клоны (4.3.1) — на временной папке APFS: каждый снапшот полный и совпадает с источником, клонируется только неизменившееся, перемещённый и вернувшийся файл, дубликаты внутри снапшота, правка клона не трогает оригинал, правленый руками и недописанный снапшот не служат оригиналом, старый формат манифеста, том без клонов, сбой клонирования, удаление старого снапшота, учёт места.
- Сохранность данных в локальном назначении — замки Finder, папки только для чтения и со списком доступа «запретить удаление», нечитаемые папки источника и назначения, ссылка вместо пути источника, служебные имена на верхнем уровне и глубже, прерванное удаление, оставшаяся папка в `/Volumes` (и путь к ней через ссылку или другое написание), пустой или ведущий наружу `slug`.
- Сжатые APFS файлы — на настоящем сжатом файле (`ditto --hfsCompression`, флаг проверяется): каждый снапшот и догон на другой диск целые, клон остаётся сжатым клоном; испорченный прежней версией снапшот не служит оригиналом; клон не того размера заменяется копией.
- Рабочие папки с замками, папками только для чтения и «запретить удаление»: доставка пакета, новый пакет на месте недоставленного, отмена, отключение устройства посреди копирования, упавшая команда, перенёсшая оригинал. Исчезнувшие во время обхода и копирования файлы и папки.
- Интеграционные: `LocalFolderDestination` на временной папке; `RcloneDestination` на rclone-бэкенде `local`, без сети.
- UI проверяется запуском приложения вручную.
