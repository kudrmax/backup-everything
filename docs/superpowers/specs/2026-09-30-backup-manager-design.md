# Backup Everything — дизайн

Дата: 2026-09-30. Статус: на ревью.

## 1. Цель

Личное macOS-приложение, которое в одном месте знает про все бэкапы Макса: что, откуда, куда, когда делалось в последний раз и что просрочено. Работает в фоне, почти не потребляет ресурсов, автоматизирует то, что можно автоматизировать, а для остального хранит инструкцию и напоминает.

Критерии успеха:

- Новый источник или назначение добавляется через UI, без правки кода.
- Один взгляд на menu bar отвечает на вопрос «всё ли в порядке с бэкапами».
- Приложение в простое не нагружает систему: нет опроса диска, нет постоянных таймеров.
- Бэкап либо записан целиком, либо не существует. Последняя успешная копия не теряется никогда.
- Все данные приложения лежат в одной читаемой папке, которая бэкапится как обычный источник.

## 2. Что сказал Макс и что решено

Сказано Максом:

- Источники: парольник (сейчас Bitwarden, позже «Пароли» macOS), iOS-приложение финансов (CSV), Google Photos, Obsidian, GitHub (все репозитории или список), Claude.
- Назначения: внешний HDD, папка на диске, облако.
- Иконка в menu bar и полноценное окно.
- Хранение версий с увеличивающимися интервалами (GFS).
- Для ручных экспортов: оригинал после подхвата удалять или оставлять — настройка на источник, по умолчанию удалять.
- Облако через rclone сразу в MVP.
- Шифрования в MVP нет, добавится позже.
- В MVP для неавтоматизируемых источников достаточно инструкции, заданной при создании источника.
- Экспорт Claude отдаёт не архив, а манифест со ссылками на архивы. Для таких источников нужен полуавтоматический тип: последовательность шагов, где одни делает человек, а другие — команда в терминале. В копию Claude попадают только архивы, манифест не нужен.
- Файлы в «Загрузках» узнаются по именам. Переименование загрузок в браузере (Arc) Макс отключает.
- Локальные копии — только на дисках APFS: диск другого формата не используется, его предлагается переформатировать. Копирует движок Apple (`copyfile`), после копирования копия проверяется; экономия места — отдельный шаг после полной проверенной копии.

Решено при проектировании:

- Стек: Swift + SwiftUI, один процесс, macOS 14+.
- Источник — это список шагов (папка, команда, файл от человека, подключить устройство); типов источника нет. Два типа назначений. Этого хватает на весь список и на комбинации вроде «подключить устройство → команда → папка».
- Шаблоны источников лежат файлами и добавляются без кода.
- Интерфейс, уведомления, сообщения и встроенные шаблоны — на английском; даты в формате en_GB (24-часовой).

## 3. Границы MVP

Входит:

- Источники из шагов четырёх видов: “Copy folder”, “Run command”, “Get a file from you”, “Connect device”.
- Назначения типов “Folder or disk” (в том числе внешний диск) и “Cloud (rclone)”.
- Расписание на источник, хранение по GFS с превью, догон недоступных назначений.
- Menu bar, окно с разделами “Overview”, “Sources”, “Destinations”, “History”, “Settings”.
- Уведомления, автозапуск при входе.
- Шаблоны источников: GitHub, Obsidian, Bitwarden, Google Photos, Claude, Claude Code, Passwords (Apple), Contacts (Apple), Finance (iOS).
- Источник “Backup Everything settings”, создаваемый при первом запуске.

Не входит:

- Шифрование.
- Мастер восстановления (есть только “Show in Finder” и «Открыть в облаке»).
- Дедупликация в облаке: туда каждый снапшот пишется целиком.
- Автоматический запуск ручных экспортов (Takeout и подобных).
- Настройка rclone remote из UI: в MVP remote создаётся в терминале по инструкции.

## 4. Модель предметной области

**Источник (Source)** — запись в конфиге:

- `id`, `name`, `steps` — список шагов, от одного и больше (4.1);
- `slug` — имя папки копий источника в назначениях (4.3). Выводится из имени при первом сохранении и больше не меняется, в том числе при переименовании. Имена папок удалённых источников запоминаются в `config.json` (`retiredSlugs`) и новым источникам не выдаются: источник с именем удалённого получает папку `photos-2`, а копии удалённого остаются нетронутыми в `photos`;
- `schedule`: `daily | weekly | monthly | manual` (только по кнопке);
- `retention`: `{daily, weekly, monthly, yearly}`;
- `destinationIds`: список назначений;
- `description`: одна-две фразы о том, что именно бэкапится (показывается под именем источника и при наведении на имя в обзоре);
- `instructions`: шаги, которые должен сделать человек (установка, вход, ручной экспорт), в Markdown; показывается в UI и в уведомлениях. Описание и инструкция — разные поля, шаблон задаёт оба;
- `icon`: необязательный значок — имя PNG-файла в `icons/`. Любой значок источника (свой или системный) рисуется на полупрозрачной серой плитке со скруглением, чтобы ряд был ровным. Любая выбранная картинка приводится к PNG 128×128; файлы, на которые не ссылается ни один источник, уходят в Корзину — только после того, как настройки прочитаны или успешно записаны, и по ним; если `config.json` не читается, значки не трогаются;
- `enabled`.

**Назначение (Destination)**: `id`, `name`, `type`, параметры типа, `expectedEvery` — как часто назначение обязано быть доступным: `always` (по умолчанию для облака и папки на внутреннем диске) или интервал «не реже чем раз в N дней» (для внешнего диска, например 30).

**Снапшот (Snapshot)** — одна версия одного источника в одном назначении. Идентифицируется временем сбора данных.

**Прогон (Run)** — одна попытка забэкапить источник: время, результат по каждому назначению, текст ошибки, размер.

**Долг (Debt)** — пара «источник, назначение», для которой бэкап не доставлен, потому что назначение было недоступно или запись упала.

### 4.1. Шаги источника

Типов источника нет. У источника есть расписание, назначения, хранение и список шагов, которые выполняются по очереди. Видов шагов четыре:

| Шаг | Кто делает | Параметры | Что даёт копии |
|---|---|---|---|
| Copy folder | приложение | `path` (папка или файл), `excludes` (glob) | содержимое папки |
| Run command | приложение | `command`, `timeoutSeconds` | то, что команда положила в `BACKUP_OUTPUT_DIR` |
| Get a file from you | человек, приложение ждёт | `instructions`, `watchPath`, `filePattern` (glob), `fileMode` (`single` или `multiple`), `includeInCopy`, `removeOriginal` | файлы, если `includeInCopy`; иначе они лежат в `BACKUP_INPUT_DIR` для следующих команд |
| Connect device | человек, приложение ждёт | `instructions`, `path` | ничего: шаг ждёт, пока путь появится (устройство подключено) |

**Что попадает в копию.** Источник из одного шага “Copy folder” отдаёт папку как есть, без промежуточной копии. Если `path` — символическая ссылка, берётся то, на что она указывает (у одного файла — под именем ссылки); ссылки внутри папки копируются как ссылки. Папка внутри, которую приложение не может прочитать (права, защита macOS), — ошибка сбора: копия без её содержимого выглядела бы полной. Исключённые папки не читаются вовсе. Папки читаются целиком, со всеми именами: имена, начинающиеся с `._`, — обычные файлы человека (Foundation их в списках папок не показывает, поэтому приложение читает папки само). Исключение — диски без собственных расширенных атрибутов (exFAT, FAT, часть сетевых шар; узнаётся по возможностям тома): там атрибуты файла `x` хранятся в файле-спутнике `._x` рядом с ним. Такой спутник, если рядом есть `x` (без учёта регистра и формы Unicode), — не файл, а атрибуты `x`: он не копируется отдельно, а атрибуты переезжают вместе с `x`. `._x` без своего `x` и любые `._` на APFS копируются как файлы. Если возможности тома узнать не удалось, ничего не пропускается. Имя, байты которого не UTF-8 (так бывает на FAT, записанном другой системой, или на повреждённом диске), не читается и не находится по пути, поэтому оно — ошибка сбора “A file name in “<папка>” is not valid UTF-8 (written by another system or a damaged disk), so it can’t be read or copied faithfully. Rename it.”, а не пустое имя. Шаг “Copy folder” в источнике из нескольких шагов копирует так же, как запись в локальное назначение (4.3): движком Apple, ровно то, что в списке, с проверкой копии по списку, и ничего не пишет поверх того, что уже лежит в `BACKUP_OUTPUT_DIR`: если там уже есть файл, папка или ссылка с тем же именем (например, от предыдущего шага), шаг падает с ошибкой ““…” already exists in the copy, so nothing was written over it: …”, а лежавшее остаётся как было (по ссылке копирование не пишет). Что лежит в `BACKUP_OUTPUT_DIR`, приложение читает по всем именам; имя не в UTF-8 там — ошибка шага с тем же текстом, что при сборе, а не «пустая папка». В остальных случаях шаги работают в рабочих папках запуска (`BACKUP_INPUT_DIR`, `BACKUP_OUTPUT_DIR`, `BACKUP_SCRATCH_DIR`, общие для всех шагов), и копией становится `BACKUP_OUTPUT_DIR`. Пустой результат — ошибка, снапшот не создаётся. Источник без шагов человека собирает копию в своей папке запуска в `staging/`. Команда могла перенести туда оригиналы человека, поэтому то, что лежит во входной и выходной папках запуска, который не довёз копию ни в одно назначение (сбор упал, все записи упали, результат оказался негодным), уходит в Корзину, а не удаляется; остальное (черновая папка, запись об идущей команде) удаляется. Результат, доставленный хотя бы в одно назначение, удаляется: копия уже есть, остальные назначения догоняют её. Если убрать в Корзину упавший сбор не удалось, к его ошибке дописывается “… What the step had added could not be moved to the Trash: …”, а остаток убирается так же при следующем запуске приложения.

**Источник без шагов человека** (только папки и команды) запускается по расписанию или кнопкой “Run” и при каждом запуске, включая догон, собирает копию заново.

**Источник с шагом человека** (файл или устройство):

- Шаг человека в начале источника ждёт, только когда источник его ждёт: подошёл срок по расписанию (то же, что автоматическое нажатие “Run”) или нажата “Run”. Пока источник не ждёт, приложение папки и устройства не трогает. У источника “Manual only” ожидание включается только кнопкой. Шаг человека после автоматических шагов ждёт сам: запуск уже идёт.
- Пока ждёт шаг, начатый сроком, источник жёлтый: “time to export” (файл) или “time to connect” (устройство), и раз в сутки приходит напоминание. Начатый кнопкой — спокойное “waiting for a file” / “waiting for the device” без напоминаний; такое ожидание можно отменить кнопкой “Cancel: stop waiting” (собранное в запуске уходит в Корзину). Ожидание по сроку не отменяется: это напоминание, оно держится до бэкапа.
- Положение запуска хранится в `state.json` (`chain`: номер и `id` шага, кто начал) и переживает перезапуск приложения; прерванная команда запускается заново с начала своего шага. Повтор начинается с чистого места: вместе с положением запоминается, что лежало в `BACKUP_OUTPUT_DIR`, когда шаг начался (`outputAtStepEntry`), и всё, что прерванная попытка успела туда добавить, перед повтором уходит в Корзину; если убрать не удалось — ошибка шага. Так же упавший автоматический шаг сразу отправляет в Корзину всё, что успел добавить в `BACKUP_OUTPUT_DIR` (а не удаляет: команда могла перенести туда оригиналы); если это не удалось, шаг заканчивается ошибкой, а недоубранное не считается тем, что лежало в начале шага, — повтор снова попробует его убрать. Положение, сохранённое прежней версией приложения, этого списка не знает, и тогда ничего не убирается. Выходная папка, которой ещё нет (такое положение на первом шаге “Connect device”: рабочие папки запуска ещё не созданы), считается пустой, а не ошибкой шага. Списки, сохранённые версиями, читавшими папку через Foundation, не показывали имён на `._` (у таких списков нет отметки `outputAtStepEntryIsComplete` / `outputAtDeviceStepIsComplete`): для них имена на `._` при уборке считаются лежавшими там с начала шага и остаются; новый список шага пишется полным и с отметкой. Шаг “Get a file from you” тоже повторяется с чистого места, но по-своему (его файлы могут быть единственной копией человека): см. ниже. Если шаги отредактировали так, что на текущем месте оказался другой шаг, запуск начинается заново, собранное уходит в Корзину.
- Результат последнего шага переносится в `pending` и доставляется оттуда: долг каждому назначению записывается до начала доставки, догон идёт из `pending`, пакет уходит из `pending` после доставки во все назначения (в Корзину, если его составляют забранные у человека файлы с `removeOriginal`, иначе удаляется). Доставка, закончившаяся, когда приложение уже выходит, не записывается (см. выход из приложения в описании команд), поэтому и пакет остаётся в `pending`: долги открыты, и следующий запуск доставляет его заново, а не остаётся с долгами, которым не из чего копировать. Ошибка при этом не теряется: она дописывается к результату доставки (“Could not clear the work folder: …”). Устройство поэтому читается один раз, и догон на отключённый ранее диск не требует подключать устройство снова.
- Если в источнике есть шаг “Connect device”, сразу после того как результат лёг в `pending` (до доставки в назначения), приходит уведомление “Safe to disconnect”.
- “Back up everything again” запускает источник с шагом человека, только если его первый шаг не придётся ждать: папка, команда или уже подключённое устройство. Ожидание файла не включает.

**Шаг “Get a file from you”:**

- Файлы с расширениями незавершённой загрузки (`.crdownload`, `.download`, `.part`, `.tmp`) и пустые файлы не подхватываются. Пока в папке есть любая незавершённая загрузка или подходящий файл менялся меньше 5 секунд назад, подхват откладывается. Браузеры называют недокачанные файлы по-разному, поэтому сопоставления по имени нет.
- Первый шаг берёт файлы новее последнего подхвата этого источника (или его создания) — в том числе скачанные до нажатия кнопки. Шаг в середине — файлы, появившиеся после предыдущего шага.
- `fileMode = single`: как только файл полностью скачан, он забирается сам. `fileMode = multiple` (многотомный Takeout): найденное показывается — “N files · size” с кнопкой “Pick up” — и забирается по кнопке (или “Retry step”). Кнопка недоступна, пока идёт загрузка; после неудачного подхвата она остаётся рядом с ошибкой.
- Подхват атомарный: если хотя бы один файл забрать не удалось, все остаются на месте, шаг получает ошибку “Could not pick up the files”.
- Подхват, который приложение не успело записать в положение запуска (упало или было закрыто сразу после переноса файлов), не теряет файлы и не мешает повтору. Перед переносом приложение записывает, что и откуда берёт (`chains/<sourceId>/pickup.json`); запись живёт, пока запуск не перешёл к следующему шагу. Если при следующей попытке запуск всё ещё на этом шаге (в том числе первый шаг, когда положение ещё не сохранено), подхват отменяется: перемещённые файлы возвращаются на прежнее место (а не в Корзину — это единственная копия человека), скопированные (`removeOriginal = false`) уходят в Корзину, — и шаг берёт файлы заново. Если имя занято (человек тем временем скачал файл с тем же именем), перемещённый файл возвращается рядом под свободным именем, как Finder называет вторую копию: `export-1 2.csv`, `export-1 3.csv`… (у составного расширения номер встаёт перед ним — `archive 2.tar.gz`, у имени, которое начинается с точки и другого расширения не имеет, — в конце: `.env 2`; имя занято и символической ссылкой, которая никуда не ведёт); файл человека не трогается, отмена завершается, и шаг идёт дальше, а не застревает навсегда. Если вернуть файл нельзя вовсе (папки, откуда он взят, больше нет), он остаётся в рабочей папке, шаг получает ошибку “Could not pick up the files: …” и повторяется. Нечитаемая запись забывается.
- `removeOriginal = true` (по умолчанию): файл перемещается; иначе копируется, а оригинал остаётся. Тот же файл второй раз не забирается.
- Если файл найден, но в папке есть незавершённая загрузка, источник показывает “N files · size · downloading”.
- Маски разных источников на одной папке не должны пересекаться. Пересекаются маски, под которые подходит хотя бы одно общее имя файла (`*.vcf` и `Work*` — оба берут `Work.vcf`); проверяется весь синтаксис масок (`*`, `?`, `[a-z]`, `[!…]`, `\`), регистр не важен. Папки сравниваются без учёта регистра и формы Unicode, `~/Downloads`, `~/downloads/` и путь через `..` — одна папка. Шаблон без известного имени файла поставляется с пустой маской: пока она не задана, ничего не подхватывается.

**Шаг “Connect device”:** ждёт, пока путь существует (том смонтирован). Отсутствие устройства — не ошибка. Если автоматический шаг после устройства упал, а устройства уже нет (его отключили посреди копирования), запуск возвращается к шагу устройства и снова ждёт его, без ошибки. Подключение устройства (монтирование тома) само запускает проверку, поэтому следующие шаги идут без нажатий. Если путь не задан, берётся папка следующего шага “Copy folder”. Всё, что попытка, прерванная отключением, успела скопировать, перед ожиданием уходит в Корзину. Когда устройство вернётся, все шаги после него идут заново с того, что лежало в `BACKUP_OUTPUT_DIR`, когда запуск проходил шаг устройства (`outputAtDeviceStep` в положении запуска): то, что сделали уже пройденные шаги между устройством и упавшим (они читали то же устройство), перед повтором первого из них уходит в Корзину, иначе повтор упирался бы в уже скопированные файлы. Положение, сохранённое прежней версией, этого не знает, и тогда повтор начинается с того, что лежало в начале упавшего шага. Если не удалось, запуск всё равно ждёт устройство, но остатки не считаются началом копирования: когда устройство вернётся, шаг копирования сначала снова убирает их в Корзину, а не удаётся — падает с этой ошибкой, и остатки не попадают в копию.

**Шаг “Run command”:**

- Запускается через `/bin/zsh -lc`. Ненулевой код возврата, остановка сигналом, таймаут или пустой результат — ошибка. Команда, убитая сигналом, не выдаётся за код возврата: ошибка так и говорит — “Command was stopped by a signal (Killed: 9).”. Хвост stdout и stderr (последние 4 КБ) сохраняется в историю; байты, которые не являются UTF-8, заменяются на «�», а не обнуляют весь вывод. Команда работает в своей группе процессов. По таймауту, при отмене задачи и при выходе из приложения останавливается команда вместе со всеми порождёнными ею процессами: сначала просьба завершиться (SIGTERM), затем, если не помогло, принудительно (SIGKILL; при таймауте и отмене — через 5 секунд, при выходе — через секунду). Выход по сигналу снаружи (`kill`, выход из системы — SIGTERM, а также SIGHUP и Ctrl-C — SIGINT) идёт так же, как Quit: сначала останавливаются команды, затем приложение завершается; иначе сигнал завершил бы приложение сразу, а команды остались бы работать без присмотра. Сигналы перехватывает только первая копия приложения. Команда, остановленная выходом из приложения, не сломалась: с начала выхода новые команды не запускаются, а прогон или шаг, чьи команды остановил выход, не записывается ни в историю, ни в состояние — источник не краснеет, цепочка не ждёт “Retry step”, уведомления нет. Следующий запуск приложения застаёт источник по-прежнему пора бэкапить (долги — открытыми, цепочку — на том же шаге) и делает работу заново. Команда шага цепочки записывается в `chains/<sourceId>/process.json`, команда источника без ручных шагов — в `staging/<папка запуска>/process.json` (pid и время запуска процесса). Если приложение упало или было убито, а команда осталась работать, её группу сначала останавливают: для цепочки — следующий запуск шага и “Start over”, для `staging` — следующий запуск приложения, до того как он убирает `staging`. Останавливается только тот же самый процесс (совпадает время запуска) и никогда группа с номером 0 или 1, иначе запись просто забывается. Последняя непустая строка stdout показывается как ход работы. Если упавший шаг оставил в выходной папке то, что не удалось убрать в Корзину, ошибкой шага остаётся его собственная ошибка, а неудача уборки дописывается к ней (“… What the step had added could not be moved to the Trash: …”).
- Таймаут в форме задаётся в минутах. Таймаут не кратный минуте (например, 90 секунд из `config.json`) показывается целым числом минут (округление вниз, но не меньше одной минуты) и сохраняется как был, пока число минут не изменено.
- Конфиг не хранит секретов. Командам, которым нужен токен или пароль, следует читать его из Keychain (`security find-generic-password`) или пользоваться собственной авторизацией инструмента (`gh auth`, `bw login`). Шаблоны так и написаны.

**Ошибка шага.** Упавший автоматический шаг убирает за собой всё, что успел добавить в копию, поэтому повтор начинается с чистого места. Источник без шагов человека повторяется через час (5.1). В источнике с шагом человека упавший шаг тоже повторяется сам через час — кроме команды, перед которой в этом источнике был шаг человека: она могла израсходовать то, что человек подготовил (одноразовые ссылки), поэтому ждёт “Retry step” или “Start over” (“Start over” сбрасывает запуск и сразу ждёт первый шаг). Ошибка источника из нескольких шагов называет шаг: “Step 2 of 3 “Download archives”. …”.

**Старые конфиги.** До перехода на шаги у источника было поле `kind` одного из пяти типов. Такой источник читается и превращается в шаги: «Папка» → [папка], «Команда» → [команда], «Ручной экспорт» → [файл от тебя] (общая инструкция источника переезжает в шаг), «По шагам» → те же шаги (старый ручной шаг — файл, один, `removeOriginal`), «Подключаемое устройство» → [подключить устройство, папка]. `id`, `slug`, назначения не меняются; `id` новых шагов выводятся из `id` источника и одинаковы при каждом чтении. Формат `config.json` — `schemaVersion` 2; перед первой записью в новом формате прежний файл сохраняется рядом как `config.v1.json`. Старые файлы шаблонов тоже читаются.

Шаблон Claude:

1. Шаг “Get a file from you” “Request export”: claude.ai → Settings → Privacy → Export data; по ссылке из письма скачать манифест в «Загрузки». Маска `manifest-*.json`, в копию не входит.
2. Команда “Download archives”, таймаут 60 минут. Читает из манифеста список `data_files`. Для каждого архива: если файл с именем `filename` уже лежит в «Загрузках» и изменён позже `created_at` манифеста, он считается скачанным; иначе ссылка `export_url` открывается в браузере по умолчанию в фоне (`open -g`). Если в «Загрузках» лежит одноимённый файл старше манифеста, шаг сразу завершается ошибкой с просьбой убрать его и ни одной ссылки не открывает: иначе браузер сохранил бы новый архив под именем «… (1).zip» и шаг ждал бы его до таймаута. Файл, рядом с которым лежит `.part`, считается ещё скачивающимся. Затем команда ждёт появления архивов в «Загрузках», печатая “downloaded N of M” при каждом изменении, и переносит каждый архив в `BACKUP_OUTPUT_DIR`, как только он скачан. Архив, уже лежащий в `BACKUP_OUTPUT_DIR`, считается готовым — повтор шага его ссылку не открывает. Незавершённой считается загрузка, рядом с которой лежит файл с тем же именем и расширением `.part` (Firefox), `.crdownload` (Chrome, Arc) или `.download` (Safari): такой архив не считается ни скачанным, ни старым, и его ссылка повторно не открывается. Если дождаться не удалось — ошибка со списком недостающих архивов: для недокачанных она советует дождаться загрузки или удалить прерванные файлы и повторить шаг, для остальных — запросить экспорт заново.

Ссылки экспорта одноразовые и защищены проверкой Cloudflare: без браузера (`curl`) они не скачиваются, поэтому скачивает именно браузер, в котором выполнен вход в claude.ai. После шага в браузере остаётся по вкладке на архив. Повтор шага открывает только ссылки недостающих архивов; сгоревшая ссылка лечится новым экспортом — новый манифест перезапускает цепочку.

### 4.2. Типы назначений

| Тип | Параметры | Доступность |
|---|---|---|
| Локальная папка | `path` | Путь существует и доступен на запись, том папки — APFS (4.2.1). Для внешнего диска это означает, что том смонтирован: путь внутри `/Volumes/<Имя>` доступен, только пока там смонтирован том. Обычная папка с тем же именем, оставшаяся на системном диске после неаккуратного отключения, — «недоступно», иначе копии молча писались бы на системный диск. Ссылка в `/Volumes` (“Macintosh HD” указывает на системный диск) считается томом. Проверяется то место, куда путь ведёт на самом деле: путь сначала раскрывается (ссылки по дороге, `..`), и папка внутри `/Volumes` узнаётся и под другим написанием (`/System/Volumes/Data/Volumes/…`, другой регистр букв), и через ссылку снаружи. |
| Rclone | `remote`, `path` | `rclone lsf remote:` завершился успешно за 15 секунд. Проверяется корень remote: папка бэкапов в облаке может ещё не существовать. |

Rclone:

- Используется установленный в системе `rclone` (поиск в `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin`). Если его нет, раздел “Destinations” показывает инструкцию по установке.
- Используется стандартный конфиг rclone (`~/.config/rclone/rclone.conf`). Токены облаков остаются там и не попадают в папку приложения. Создание remote — по инструкции в UI через `rclone config` в терминале.
- В облако уходят только обычные файлы: символические ссылки и пустые папки не переносятся. В локальное назначение копируется всё.

### 4.2.1. Диск назначения

Внешний диск узнаётся не по имени: любой диск (флешка, образ) можно назвать так же, и тогда копии, в том числе экспорты с паролями, ушли бы на него. Поэтому папка на внешнем диске привязана к самому диску.

- Внешний диск — путь папки ведёт в смонтированный том внутри `/Volumes` (после раскрытия ссылок, как в 4.2). Папка на системном диске (например, в домашней папке) и облако не привязываются и работают как раньше.
- Привязка — поле `disk` назначения в `config.json`: `uuid` (Volume UUID, как его читает Disk Arbitration; у exFAT и FAT он выводится из серийного номера) и `name` (имя диска на момент чтения, только для показа). Сравнивается только `uuid`. Поле необязательное: назначение без него читается как «диск не подтверждён». Foundation (`volumeUUIDString`) для FAT32 и FAT16 сообщает новый случайный UUID при каждом подключении, поэтому UUID читается через Disk Arbitration; для APFS, HFS+ и exFAT он совпадает с тем, что сообщал Foundation, и прежние привязки остаются в силе. Привязки FAT-дисков, сделанные прежней версией, не совпадут один раз: диск покажется другим, и его подтверждают заново кнопкой.
- «Диск не сообщает UUID» и «UUID не удалось прочитать» — разные вещи. Если Disk Arbitration не отдал описание смонтированного тома, диск считается неопознанным: он не совпадает ни с какой привязкой (в том числе с `uuid: null`) и не считается другим диском, назначение недоступно, а при следующей проверке UUID читается снова. Кнопки его не запоминают: “Read from connected disk” и “This is my <назначение>” показывают ошибку “Could not read the ID of the disk “<имя>”. Nothing was remembered: reconnect the disk and try again.”, привязка и черновик не меняются.
- Привязка появляется только по нажатию человека, сама — никогда (ни при первом подключении, ни по папке с копиями на диске):
  - кнопка “Read from connected disk” в строке “Disk” настроек назначения (и при создании, и при правке; доступна, только когда по пути смонтирован том) записывает в черновик текущий диск; сохраняется обычным “Save”. Если диск не сообщает UUID, явно записывается `uuid: null` — и дальше назначение принимает только диск без UUID;
  - кнопка “This is my <назначение>” под именем назначения в его настройках, когда подключён неподтверждённый или другой диск: сразу записывает текущий диск в назначение в `config.json` обычным сохранением настроек (если записать не удалось — ошибка, как у любого сохранения, привязка не меняется). Открытый черновик получает этот диск, если в нём не меняли папку.
- Смена папки в настройках сбрасывает диск в черновике: новую папку нужно подтвердить заново. Удалённое назначение уносит привязку с собой.
- Назначение на внешнем диске доступно, только если подключён подтверждённый диск. Без привязки (все прежние назначения после обновления и новые, где кнопку не нажали) или с другим диском по тому же пути назначение недоступно для всего: записи, догона, сверки копий, удаления старых копий, измерения места, списка копий в настройках и “Open copy”. Там ничего не читается для решений и ничего не пишется. Кроме проверки доступности, `LocalFolderDestination` сам отказывается читать список копий, писать, удалять, отдавать копию и мерить место (`diskNotConfirmed`, `otherDisk`, `diskUnidentified`), если диск не тот, и (`unavailable`), если подтверждённый диск не подключён: папка того же пути в `/Volumes` тогда лежит на системном диске.
- Только APFS. Если папка назначения лежит на диске другого формата (exFAT, FAT, Mac OS Extended, сетевая шара — по файловой системе тома папки или её ближайшей существующей родительской папки), назначение не используется вовсе: ни записи, ни догона, ни списка копий, ни чистки, ни подсчёта места; `LocalFolderDestination` отказывает во всём с ошибкой `unsupportedFormat`. Другой или неопознанный диск сообщается в первую очередь; формат проверяется у подтверждённого, неподтверждённого подключённого диска и у папки на системном диске (системный диск — APFS). Назначение оранжевое: коротко — “formatted as <формат>, needs APFS”, подробно — “Disk “<имя диска>” is formatted as <формат> and can’t be used. Backups need APFS: reformat it in Disk Utility (this erases it).”, в “Copies” — “The disk is formatted as <формат> — copies aren’t shown.”, у “Open copy” — “The disk is formatted as <формат>, not APFS”. Кнопка подтверждения диска не предлагается. Форматы называются так: exFAT, FAT, Mac OS Extended (HFS+), a network share (SMB/AFP/NFS/WebDAV), иначе — имя файловой системы как есть. Код, который нужен был только для записи на такие диски (пропуск неподдерживаемых атрибутов и флагов, повторное удаление имён в другой форме Unicode на exFAT, учёт спутников `._x` в папке назначения), удалён.
- “Open copy” проверяет то же: у назначения, где диск не подключён, не подтверждён, другой или неопознан, пункт неактивен с причиной в подсказке (“The disk isn’t connected”, “The disk isn’t confirmed”, “Another disk is connected”, “The disk’s ID can’t be read”); перед открытием диск проверяется ещё раз, и если он сменился, показывается ошибка “Can’t open the copy in “<назначение>”: <причина>.”, а Finder ничего не открывает.
- Как это видно: назначение жёлтое (оранжевая метка, как “time to connect”), в строке назначений обзора, в меню и в настройках:
  - другой диск — “another disk named “<имя диска>” is connected”; подробно: “Another disk named “<имя диска>” is connected. Nothing is written to it or deleted from it. If it is the disk of “<назначение>”, press “This is my <назначение>”.”
  - диск не подтверждён — “disk not confirmed”; подробно, если диска нет: “Confirm the disk for “<назначение>”: connect it and press “Read from connected disk” in its settings.”; если подключён: “Confirm the disk for “<назначение>”: if the connected disk “<имя диска>” is it, press “This is my <назначение>”.”
  - диск неопознан — “can’t read the ID of disk “<имя диска>””; подробно: “Couldn’t read the ID of the connected disk “<имя диска>”, so it isn’t known whether it is the disk of “<назначение>”. Nothing is written to it or deleted from it. The app checks again on its own; if this goes on, reconnect the disk.”; в “Copies” — “The disk’s ID can’t be read — copies aren’t shown.”;
  - в строке “Disk” настроек — запомненный диск вторичным текстом в две строки: `“<имя>”`, под ним мелким моноширинным `ID <uuid>` или `the disk reports no ID` (или одна строка `Not set`). Длинный ID сокращается посередине, полностью — в подсказке; кнопка “Read from connected disk” всегда видна целиком.
- Папки нет, хотя её диск на месте (подтверждённый диск подключён или папка на системном диске): назначение жёлтое с меткой “folder not found”, подробно — “The folder “<путь>” doesn’t exist on the disk “<имя диска>”. The app doesn’t create it itself: create it or choose another folder.” (для системного диска — без “on the disk …”), в “Copies” — “The folder “<путь>” doesn’t exist on the disk “<имя диска>” — copies can’t be seen.” Раньше здесь было “Not connected — copies can’t be seen.”, что неправда: диск подключён.
- Восстановление всегда возможно одной кнопкой: диск переформатирован, заменён или не сообщает UUID — “This is my <назначение>” (или “Read from connected disk” и “Save”) запоминает текущий диск. Уведомлений и отдельных напоминаний об этом нет.

### 4.3. Раскладка снапшотов

```
<корень назначения>/<slug источника>/<YYYY-MM-DD_HHmmss>/   (в повторяющийся час перевода часов — <YYYY-MM-DD_HHmmss±HHMM>)
    …содержимое…
    _unfinished         ← метка «пишется», кладётся первой и убирается после манифеста
    _snapshot.json      ← манифест, пишется последним
```

- Имя папки снапшота — местное время сбора. Когда часы переводят назад, час повторяется; снапшоты этого часа получают в имени смещение от UTC (`2026-10-25_023000+0200` до перевода, `2026-10-25_023000+0100` после), поэтому два бэкапа с разницей в час не получают одно имя и каждый читается как свой момент. Снапшоты, записанные в этот час прежними версиями (без смещения), остаются снапшотами. Имя со смещением однозначно и читается как тот же момент в любом часовом поясе: после переезда Mac в другой пояс такие копии не пропадают из списка и не считаются пропавшими при сверке (5.3.1). Имя без смещения по-прежнему читается в текущем поясе.
- `slug` — имя одной папки. Если в `config.json` (например, правкой руками) оказался пустой `slug` или со `/` или `..`, назначение (локальное и облачное) отказывается что-либо читать, писать и удалять для этого источника: ошибка “The folder for copies of this source is named “…”, which is not a single folder name. Nothing was read, written or deleted. Fix “slug” of the source in config.json.”. Корень назначения и чужие папки так никогда не трогаются.
- Снапшот источника — папка в папке его `slug`, манифест которой называет `id` этого источника (или не читается). Снапшот, манифест которого называет другой источник (так бывает в настройках, сделанных до запоминания имён папок удалённых источников), этому источнику не принадлежит: чистка по GFS его не удаляет и не учитывает, догон не берёт его как готовую копию, а копия с тем же именем не считается уже доставленной — запись упирается в чужую папку (см. ниже).
- Манифест содержит id и имя источника, время сбора, количество файлов, суммарный размер. У локального назначения в нём ещё список файлов копии (путь, размер, SHA-256, время изменения) и признак `sharesData` — делит ли копия данные с прошлыми (4.3.1).
- Снапшот считается существующим только при наличии манифеста. Недописанный снапшот — папка, которую приложение начало и не дописало: в ней есть метка `_unfinished` и нет манифеста. Такие папки этого источника убираются только после того, как в это же назначение успешно записан новый снапшот (или он там уже был): в локальном назначении — в Корзину, в облаке (Корзины нет) — удаляются. Папка без манифеста и без метки (например, снапшот, у которого пропал манифест, или старые недописанные папки, записанные до появления метки) снапшотом не считается и не трогается никогда.
- Если при записи на месте нового снапшота уже лежит недописанная папка с тем же именем (повтор той же копии), она убирается (в локальном назначении — в Корзину, в облаке — удаляется) и снапшот пишется заново, без остатков прошлой попытки; если там любая другая папка (без метки или чужой готовый снапшот), запись не идёт, папка не трогается, а в ошибке назван путь мешающей папки. Так работают оба типа назначений.
- Эта схема одинакова для локальной папки и rclone и не требует атомарного переименования на стороне облака.
- Файлы лежат как есть, без архивации и без проприетарного формата: снапшот открывается в Finder или в веб-интерфейсе облака без приложения.
- Локальное назначение копирует движком копирования Apple — `copyfile(3)` с `COPYFILE_RECURSIVE | COPYFILE_ALL`, тем же, которым копируют Finder и `ditto`, один вызов на каждую папку верхнего уровня источника (файлы и ссылки верхнего уровня — тем же движком по одному). Он переносит имена байт в байт (форма Unicode не меняется: «й» не раскладывается на «и» и знак краткости), данные (сжатые APFS файлы остаются сжатыми), даты, права, замок Finder (“Locked”) и другие флаги, списки доступа и расширенные атрибуты (теги, метки) файлов и папок; папки получают свои права и даты после содержимого, так что папка только для чтения всё равно заполняется. Собственного кода переноса метаданных у приложения нет. Копируется ровно то, что вошло в список источника: обратный вызов движка пропускает остальное (исключения, спутники `._x`) и сообщает об ошибках. Копирование никогда ничего не перезаписывает и не идёт по ссылкам в назначении: каждый элемент создаётся заново (`COPYFILE_EXCL`), каждая папка верхнего уровня источника копируется отдельным вызовом движка в ещё не существующую папку. Если на месте элемента уже что-то есть — файл, ссылка (в том числе на папку человека), папка, или элемент этой же копии, имя которого назначение не отличает (два файла источника с регистрозависимого диска, `A.txt` и `a.txt`, на APFS без учёта регистра), — копия останавливается с ошибкой ““<путь>” already exists in the copy, so nothing was written over it: two originals have names the destination does not tell apart (such as names that differ only in letter case), or something was already there. The copy was left unfinished so as not to pass for a complete one.”, а лежавшее не меняется. Ссылки движок создаёт после того, как запечатал их папку, — в папке только для чтения или с замком ссылка терялась бы, а любая папка со ссылкой получала бы новую дату, — поэтому каждая ссылка копируется тем же движком отдельно, перед тем как её папка запечатывается.
- Сама папка снапшота (и выходная папка шага, куда копирует “Copy folder”) свои права, замок и даты от папки источника не берёт. Исключённая папка в копию не попадает: движок её не создаёт, а папку, которая уже была на её месте, не трогает.
- Источник может лежать на любом диске (карта камеры на FAT, флешка exFAT, сетевая шара): то, что этот диск хранит о файлах, движок переносит в копию на APFS; спутники `._x` с такого диска приходят атрибутами `x` (4.1).
- Файлы, которые APFS хранит сжатыми (флаг `UF_COMPRESSED`), копируются сжатыми и в копии читаются целиком.
- Копия проверяется после записи, до манифеста: каждый элемент списка источника (с учётом исключений), который не исчез из источника, есть в копии и того же типа (файл, папка, ссылка); файл — того же размера (как его видят читатели, у сжатого — после распаковки), ссылка — с той же целью. На элемент — один `lstat`, содержимое заново не читается; два элемента списка не могут оказаться одним элементом копии (сверяются диск и номер файла) — иначе та же ошибка “already exists in the copy”. Файл, изменившийся во время копирования (живой файл), может отличаться размером — в копии остаётся прочитанное. Если оригинал файла другого размера исчез во время копирования (временный файл живой папки вырос и пропал), в копии лишь часть файла: эта часть убирается из копии обычной уборкой (замок и список доступа снимаются) и в манифест не попадает — так же, как файл, исчезнувший до копирования; ошибкой бэкапа это не считается. Только если убрать её не удалось (например, папка копии только для чтения), запись падает с ошибкой “The original of “…” vanished while it was being copied, so the copy holds only part of it. The copy was left unfinished so as not to pass for a complete one.”; если исчез весь источник или диск — ошибка об исчезнувшем источнике; если оригинал нельзя посмотреть (нет прав, ошибка диска) — ошибка с причиной. Манифест составляется по копии до проверки, а проверка идёт после: элемент, пропавший из копии раньше, чем её прочитали для манифеста, не даёт «готовую» копию с манифестом без него. Любое другое расхождение — ошибка записи с путём первого расхождения в копии: ““…” is missing from the copy although its original is still there. The copy was left unfinished so as not to pass for a complete one.” или ““…” in the copy is not as its original (another type, size or link target). The copy was left unfinished so as not to pass for a complete one.”. Копия остаётся недописанной (`_unfinished`, без манифеста), не считается доставленной, старые копии не чистятся. Так же проверяется результат шага “Copy folder” в рабочей папке.
- Файл или папка, исчезнувшие после того, как их папку прочитали (живые папки, кэши), в снапшот не попадают и ошибкой не считаются; от исчезнувшей папки может остаться пустая. Так — только пока сам источник на месте: его папка (или файл) существует, это та же папка, что при начале обхода (тот же диск и тот же номер файла), а ближайшая оставшаяся папка над исчезнувшим лежит на том же диске, на котором исчезнувшее было при обходе, и на том же, на котором при обходе была сама эта папка. Если диск источника отключили или папку источника переименовали или подменили посреди обхода или копирования, недостающее не «исчезло»: запись падает с ошибкой “The source “…” disappeared during the backup (disk disconnected?). The copy was not finished.”, снапшот остаётся недописанным (метка `_unfinished`, без манифеста) и не считается доставленным, а старые полные копии не чистятся. Так же с диском, подключённым внутри папки источника: когда его отключают, на его месте остаётся пустая папка на диске источника, и его файлы тоже не «исчезли» — ошибка “The disk mounted at “…” inside the source disappeared during the backup (disk disconnected?). The copy was not finished.”. Если исчезло всё, что было в источнике, пустая копия не дописывается: ошибка “Every file of the source disappeared while it was being copied. An empty copy is not created.”, снапшот остаётся недописанным. Файл, который есть, но не читается, — по-прежнему ошибка.
- Манифест локального снапшота составляется по готовой копии, перед её проверкой (проверка его подтверждает): какие файлы и ссылки в ней лежат, размер, SHA-256 и дата каждого файла, их количество и суммарный размер. Исчезнувшие файлы в нём не значатся. Файл копии, который не прочитать для манифеста, — ошибка с полным путём: ““<путь>” in the copy could not be read back for the list of its files: <причина> The copy was left unfinished so as not to pass for a complete one.”. Те же числа записываются в историю прогона: по первой копии этого прогона, о которой назначение знает, что в ней лежит (локальное назначение знает, облако — нет); если такой копии нет — по обходу источника.
- Имена `_snapshot.json` и `_unfinished` на верхнем уровне снапшота принадлежат приложению. Если у источника на верхнем уровне лежит файл или папка с таким именем (без учёта регистра и формы Unicode), сбор заканчивается ошибкой “… has the name Backup Everything gives its own file in every copy. Rename it, move it into a subfolder or add it to the exclusions.”, снапшот не начинается: иначе недописанная копия с чужим `_snapshot.json` считалась бы готовой. Глубже такие имена — обычные файлы: они копируются, в том числе при догоне.
- Локальный снапшот удаляется так: сначала с самой папки снимается замок, и она переименовывается в `<имя>.deleting`, затем удаляется целиком — с каждого элемента снимаются замок и списки доступа, папки открываются владельцу. Если удаление прервалось, остаток уже не похож на снапшот (имя не читается как дата) и дочищается после следующей успешной записи в это назначение. Остаток, который и тогда не удалось удалить, не замалчивается: он попадает в предупреждение доставки (“Could not finish deleting old copies: …”) при каждой записи, пока не удалится, а GFS при этом применяется к остальным копиям. Других папок с суффиксом `.deleting` приложение не трогает. Удаление видит все имена, в том числе `._…` (иначе папка с таким файлом не удалилась бы). Имя, байты которого не UTF-8, останавливает удаление папки до того, как в ней что-либо удалено; ошибка называет папку. Занятое место тоже считается по всем файлам, включая `._…`; папка, которую не прочитать, и имя не в UTF-8 в подсчёт не входят. Так же удаляются рабочие папки.

### 4.3.1. Неизменившиеся файлы в локальном назначении

У источника есть выключатель “Save space” (`savesSpace`, по умолчанию включён, в том числе у источников из старых настроек). Включён — неизменившееся не записывается заново, как описано ниже; выключен — каждый снапшот пишется целиком.

Каждый снапшот сначала пишется целиком и проверяется (4.3) — для записи нужно место на полную копию; при нехватке места запись падает с ошибкой “The destination is out of space.”, копия остаётся недописанной. Затем, если выключатель включён, файлы новой копии, совпадающие с тем же файлом предыдущей копии, становятся APFS-клонами его. Клон — отдельный файл с общими данными на диске, поэтому правка файла в одном снапшоте не меняет другие, а удаление снапшота не трогает остальные. Восстановление — скопировать папку нужного снапшота, ничего собирать не нужно.

- Совпадение: в предыдущей копии (самой свежей готовой копии этого же источника — по `sourceId` манифеста — в этом назначении) лежит файл по тому же пути, того же размера и с тем же SHA-256 (по манифестам обеих копий), и у обоих файлов одинаковые метаданные: права, владелец, флаги (в том числе сжатие `UF_COMPRESSED`), даты изменения и создания, расширенные атрибуты и список доступа. Переименованный и перемещённый файл, файл, вернувшийся после удаления, и одинаковые файлы внутри одной копии хранятся целиком.
- Файл предыдущей копии используется, только если с записи его размер и время изменения не менялись, а его настоящий размер равен размеру файла источника; файл, который правили руками, не служит оригиналом. Так копии, испорченные прежней версией (сжатые файлы в них стали пустыми, а манифест записал размер 0 с хэшем источника), не размножаются: такой файл пишется заново целиком.
- Хэши в манифесте считаются по готовой копии, а не по оригиналу: если оригинал менялся во время копирования, манифест всё равно описывает то, что лежит в снапшоте.
- Замена атомарна: клон делается рядом с файлом под временным именем `.backup-everything-clone-…`, проверяются его размер и SHA-256 (клон читается целиком и должен дать хэш, записанный в манифест для нового файла), и он переименовывается поверх файла, так что файл в каждый момент целый. Так файл предыдущей копии, изменённый на месте с тем же размером и датой, не переносит порчу в новую копию. Папки, в которых файлы заменены, сохраняют свои даты. Любая неудача (клон не сделался, вышел не того размера или содержимого, файл нельзя заменить: у него замок или запрет удаления, папка только для чтения) оставляет полный файл и ошибкой бэкапа не считается; временный клон удаляется. Если временный клон удалить не удалось, он остался бы в копии чужим файлом: запись падает с ошибкой “A temporary file “…” made while saving space could not be removed from the copy: <причина> The copy was left unfinished so as not to pass for a complete one.”, копия остаётся недописанной. Манифест составлен до замены и остаётся верным: у клона то же содержимое и те же метаданные.
- Файл с замком (`uchg`/`uappnd`, в том числе системные флаги) и файл в папке только для чтения общих данных не получают никогда: такие файлы хранятся в каждой копии целиком (клон нельзя переименовать поверх них).
- Если том назначения не поддерживает клоны, снапшот пишется целиком, со списком файлов и `sharesData = false`.
- Снапшоты, записанные до появления клонов (без списка файлов), оригиналами не служат: первый снапшот после обновления пишется целиком.
- Выключатель неактивен (выключен и без руки-курсора), если ни одно выбранное назначение не позволяет клоны: облако, диск не APFS, или назначения не выбраны. Если позволяют не все, рядом подпись “full copies in “Cloud”” — там снапшоты всё равно пишутся целиком; если ни одно — “not possible in …”. Подсказка у названия объясняет, что это и где работает. Что позволяет отключённый диск, приложение помнит с последнего подключения (проверяется вместе с занятым местом); диск, который ещё ни разу не был подключён, считается позволяющим — проверка будет при записи.
- «Сколько занимают копии» у локального назначения — одно число: сколько места реально занято на диске. Обходятся все файлы папки назначения, у каждого берётся занятое место из файловой системы; данные, общие у клонов, считаются один раз (APFS сообщает у файла номер группы клонов и сколько байт принадлежит только ему). От манифестов подсчёт не зависит. На диске не APFS — просто сумма занятого места файлов.

### 4.4. Хранение (GFS)

Правило на источник: «последняя копия за каждый из N последних дней с копиями, одна в неделю за последние M недель, одна в месяц за последние K месяцев, одна в год за последние Y лет». Несколько копий за один день сворачиваются в самую свежую. Значения по умолчанию: 7 / 4 / 12 / 0.

Алгоритм (семантика restic и borg):

```
keep(snapshots, rules):
  sorted = snapshots по убыванию времени
  keepSet = { sorted[0] }                 // последняя копия живёт всегда
  для каждого уровня (day, week, month, year) с n > 0:
    seen = []
    для s в sorted:
      b = корзина(уровень, s.date)        // день | ISO-неделя | месяц | год, локальный календарь
      если b уже в seen: пропустить
      если len(seen) == n: стоп
      seen.append(b); keepSet.add(s)
  удалить snapshots \ keepSet
```

- Считаются только непустые корзины: пропущенные дни не съедают квоту.
- Применяется отдельно для каждой пары «источник, назначение» и только после успешной записи нового снапшота. Учитываются и удаляются только снапшоты самого источника (4.3): копии другого источника в той же папке не занимают корзины и не удаляются.
- Форма источника показывает превью: какие из существующих снапшотов останутся и какие удалятся при текущих числах.

## 5. Поведение

### 5.1. Расписание

- Источник пора бэкапить, когда `последний плановый прогон + интервал ≤ сейчас`. Источник, который ещё ни разу не запускался, пора бэкапить сразу.
- После неудачного сбора данных или неудачной записи повтор идёт не раньше чем через час — и для плановых прогонов, и для догона. Исключение — упавшая команда после шага человека: она не повторяется сама (см. 4.1).
- Планировщик держит один таймер до ближайшего срока и пересчитывает его после каждого прогона, изменения конфига, пробуждения Mac и монтирования тома. Периодического опроса нет.
- Если Mac спал в момент срока, прогон стартует после пробуждения.
- Прогоны выполняются строго по одному.

### 5.2. Один прогон

1. Источник собирает данные (папка, результат команды, подхваченный пакет или результат цепочки шагов).
2. Для каждого назначения источника:
   - доступно — записать снапшот (метка, файлы, манифест, снятие метки), затем убрать недописанные папки, применить GFS; ошибка этой чистки — предупреждение, а не провал доставки. Предупреждение доставки запоминается для пары «источник, назначение» (`deliveryWarnings` в `state.json`) до следующей доставки в это назначение без предупреждения и делает источник жёлтым (5.5): иначе неудаляемые старые копии копились бы на диске при зелёном “All good”. Если не удалось убрать недописанные папки или получить список снапшотов, GFS не применяется. Снапшот, который не удалось удалить, не мешает удалить остальные: удаляются все, какие получится, а в предупреждении перечислены ошибки;
   - недоступно или запись упала — записать долг.
3. Записать прогон в историю, обновить статус, при ошибке показать уведомление.

Сбой в одном назначении не влияет на остальные.

### 5.3. Долги и догон

- При монтировании тома, пробуждении и перед каждым плановым прогоном планировщик проверяет долги.
- Источник собирается один раз за запуск; назначение, которое запуск пропустило (было отключено, упало или добавлено позже), получает уже сделанную копию. Порядок выбора, как только должник доступен: пакет из `pending` (у источников с шагом человека); иначе самая свежая копия источника (4.3: не чужая копия в той же папке) на другом доступном его назначении — переносится как есть, под тем же именем, источник заново не собирается (GitHub ничего не качает, устройство подключать не нужно; при равной дате берётся локальное назначение, облако скачивается во временную папку); иначе, если готовой копии нет нигде, источник без шагов человека собирается заново, а источник с шагом человека остаётся должен до своего следующего бэкапа (поиск копии повторяется раз в час, значок назначения в строке — “waiting to be connected”). Пакет удаляется из `pending`, когда доставлен во все назначения.
- После догона на внешний диск приходит уведомление “Safe to disconnect the disk”.
- Назначение с интервалом `expectedEvery` (“Can stay unplugged” · “up to N days”) не обязано быть подключено постоянно. Каждый долг помнит, есть ли пропущенный бэкап на другом назначении источника (`elsewhere`: запуск доставил его куда-то ещё; для пропавшей копии — у источника есть копия на другом назначении; если хоть один пропущенный бэкап нигде больше нет, флаг снимается до закрытия долга). Если какого-то пропущенного бэкапа больше нигде нет (например, диск — единственное назначение источника), напоминание приходит сразу. Иначе, пока с последнего успешного догона (`lastCaughtUp`: доставка, после которой назначению никто не должен; долги выключенных источников при этом не считаются, 5.3 ниже) прошло меньше интервала, долги не влияют на статус и не вызывают напоминаний; когда интервал вышел — напоминание. Оно повторяется раз в сутки. Текст: “Connect “HDD”” + “The backup of “X” exists nowhere else. It will be written as soon as you connect the disk.” или “The disk hasn’t been connected for a while. Copies are on other disks, but this one needs updating too.”. В настройках назначения правило написано текстом под строкой срока; в подсказке значка назначения в строке источника — “a copy is on “…”” или “this backup exists nowhere else — connect the disk”; в подсказке назначения внизу обзора — что больше нигде нет или когда напомню.
- Сколько бы плановых прогонов ни было пропущено, догон создаёт один свежий снапшот на источник, а не по снапшоту за каждый пропущенный день.
- Догон готовой копией (с другого назначения или из `pending`) закрывает только проблемы доставки. Если последний сбор источника упал (ждёт повтора через час), такая старая копия не делает источник зелёным и не отменяет повтор: ошибка сбора остаётся, пока сбор не пройдёт. Догон, который собрал источник заново (готовой копии не было нигде), — это успешный сбор: он снимает ошибку. Готовая ли это копия, движок записывает в прогон фактом (`deliversAnOlderCopy`: копия с другого назначения или пакет из `pending` при догоне), а не угадывает по дате в имени копии — имя, прочитанное в другом часовом поясе, может оказаться позже самого догона. По той же причине «последний успешный сбор» не ставится позже окончания прогона. В истории, записанной до этого поля, готовой копией считается только перенесённая с другого назначения (`copiedFrom`).
- Долги выключенного источника ждут его включения: догон их не закрывает, поэтому они не влияют на статус, не дают напоминаний “Connect …”, не будят планировщик и не мешают назначению считаться догнанным: доставка, после которой остались только такие долги, обновляет `lastCaughtUp`, иначе срок “up to N days” отсчитывался бы от давней даты и диск просили бы подключить сразу. Сами долги сохраняются — после включения догон и напоминания продолжаются с того же места.

### 5.3.1. Сверка с назначениями

Приложение не полагается только на собственные записи: оно проверяет, что копии действительно лежат в назначении.

- На каждом `tick()` (запуск приложения, открытие окна, пробуждение, подключение диска, плановый срок) для каждого доступного назначения проверяется, что последняя доставленная копия каждого источника на месте. Локальные назначения сверяются каждый раз, облачные — не чаще раза в сутки.
- Если копии нет, паре «источник, назначение» записывается долг, и в этом же `tick()` он закрывается по правилам догона (5.3). Приходит уведомление “Copy missing”, в “History” остаётся запись догона.
- Если источнику добавили новое назначение, копия туда делается сразу, не дожидаясь планового срока; уведомления “Copy missing” при этом нет. Поэтому после каждого сохранения настроек через пару секунд идёт `tick()`.
- Для копий, сделанных до появления сверки, последняя доставленная копия определяется по истории прогонов — только по прогонам, начатым не раньше, чем пару «источник, назначение» начали ждать в нынешнем месте назначения (`expectedSince`, 6): копия, доставленная до переезда назначения или до того, как его убрали из источника, о нынешнем месте ничего не говорит. Если ни имени, ни такого прогона нет, копией считается только копия этого источника (по `sourceId` манифеста): копия другого источника с тем же именем папки — не его копия, и назначение получает свою.
- Сверка, нашедшая копию, заводит факт доставки, если его нет (назначение вернули источнику, назначение переехало туда, где копии уже лежат, состояние без даты): имя найденной копии в `lastDelivered` и момент её сбора по имени в `deliveredAt`. Без этого назначение до следующего бэкапа выглядело бы как “no copy yet”, хотя копия на месте.
- **Факты принадлежат месту.** Назначение, у которого поменяли папку, remote или путь в облаке, или подтверждённый диск (по Volume UUID; первое подтверждение и сброс — тоже), — новое место. Всё известное о копиях в нём забывается: имя и дата последней копии каждого источника, предупреждение после доставки, `lastCaughtUp` и `lastVerified`; пары с ним ждут копию с момента переезда. Поэтому до доказательства копии на новом месте источник не зелёный (“no copy yet”), сверка идёт сразу (и облако — не через сутки), копии нет — долг без уведомления “Copy missing” и догон в том же `tick()`; копия уже лежит там — факт заводится по ней (выше). Имя назначения, режим подключения и имя, под которым прочитан диск, местом не являются. Место, у которого собраны факты, хранится в состоянии (`location`, 6) и сверяется с настройками при каждом чтении состояния ядром (`StateReducer.reconcile`, в том числе для окна), так что правка настроек сразу видна в статусе.
- Недоступное назначение и назначение, список копий которого не удалось получить, не сверяются: отсутствие ответа не считается пропажей. Пустой список локальное назначение отдаёт только когда папки источника в нём нет; папка, которую нельзя прочитать, — ошибка, а не «копий нет».

### 5.4. Ошибки

- Недописанный снапшот не считается снапшотом (нет манифеста). Убирается только после успешной записи нового снапшота (5.2, 4.3).
- Чистка по GFS идёт только после успешной записи нового снапшота. Снапшоты, удалённые чисткой, удаляются безвозвратно, минуя Корзину.
- Путь источника исчез, источник не дал ни одного файла или часть его не читается — ошибка; существующие снапшоты не трогаются. Файл или папка внутри источника, исчезнувшие во время обхода, — не ошибка: их просто нет в копии (4.3). Исчезновение самого источника посреди обхода или копирования (отключённый диск, переименованная папка), как и диска, подключённого внутри папки источника, — ошибка, которая говорит, что исчезло (4.3). Если исчезло всё содержимое источника, это ошибка, как пустой результат.
- Если корневая папка локального назначения отсутствует (диск не подключён), приложение её не создаёт и ничего не пишет по этому пути.
- В папке источника в назначении приложение удаляет только папки с именем снапшота (и их остатки `<имя>.deleting`, 4.3); посторонние файлы и папки не трогает.
- Последняя успешная копия не удаляется при любых значениях правила. Только что записанный снапшот чисткой этого же прогона не удаляется никогда.
- Источник, все назначения которого удалены, считается источником без назначений: не запускается и отмечается в статусе.
- Файл настроек, который существует, но не читается, — ошибка; пустыми настройками он не подменяется.
- Нехватка места: приложение не удаляет ничего сверх правила, помечает ошибку и уведомляет.
- Ошибки в истории и уведомлениях формулируются человеческим языком с техническими деталями под спойлером.

### 5.5. Статус в menu bar

| Статус | Условие |
|---|---|
| Спокойный | Каждый включённый источник, от которого ждут копию (уже запускался или уже доставлял), доказал свежую копию в каждом своём назначении (правило ниже), и других проблем нет. Отсутствие известных проблем само по себе спокойным статусом не считается. |
| Жёлтый | Источник ждёт шага человека, а запуск начат сроком (“time to export”, “time to connect”); есть найденные файлы, ждущие “Pick up”; назначение `always` недоступно и имеет долг; у назначения с интервалом вышел срок подключения; у источника не выбрано ни одного назначения; у источника нет свежей копии хотя бы в одном назначении (правило ниже); последняя доставка источника в какое-то из его назначений прошла с предупреждением (не удалось убрать старые копии или рабочую папку, 5.2). Ожидание, начатое кнопкой (“waiting for a file”, “waiting for the device”), статус не портит. |
| Красный | Последний прогон какого-либо источника завершился ошибкой, либо источник, который уже запускался, давно без бэкапа (“no backup for a long time”). Давность считается в том же ритме назначений, что и свежесть (ниже): для каждой копии источника конец её ритма — следующий бэкап по расписанию от момента её сбора, а на диске “Can stay unplugged · up to N days” — не раньше чем через N дней после сбора; красный — когда после конца ритма пропущено ещё два бэкапа по расписанию у всех копий, то есть даже самая свежая копия где угодно среди назначений источника слишком стара. Запуск, который никуда не доставил копию, бэкапом не считается. Если копий нет ни в одном назначении, отсчёт идёт от момента, с которого назначение ждёт копию (`expectedSince`: добавление к источнику или переезд назначения; для пар, существовавших до появления этого поля, — создание источника): новое или только что сменённое назначение без копии — оранжевое “no copy yet”, а не красное. Источник, который ещё ни разу не запускался, и источник без расписания (“Manual only”) красными по давности не бывают. |

**Свежесть копий.** Статус источника строится из фактов, а не из отсутствия известных проблем. Для каждого назначения источника берётся самая свежая его копия там и момент её сбора (`deliveredAt` в `state.json`, 6; для перенесённой готовой копии — момент сбора этой копии, а не догона). У каждого назначения свой ритм:

- назначение “Always connected” — копия свежая до следующего бэкапа по расписанию источника, отсчитанного от момента сбора копии, плюс час (`retryInterval`, время на сам прогон). У источника без расписания (“Manual only”) копия свежая, пока назначению не должны более новую (нет долга);
- назначение “Can stay unplugged · up to N days” — ровно правило срока подключения из 5.3: пока долга нет или срок подключения не вышел, копия свежая; вышел — нет;
- назначение, где копии нет вовсе, свежей копии не имеет.

Источник зелёный, только если свежая копия есть в каждом его назначении и нет ошибок и других проблем. Иначе он жёлтый с причиной: какому назначению не хватает свежей копии и почему — берётся из состояния назначения (“unavailable”, “time to connect”, “disk not confirmed”, “another disk named … is connected”, “formatted as exFAT, needs APFS”, “folder not found”, “waiting for connection”), иначе из последней записи туда (“couldn’t write: …”), иначе “waiting to be written”, “no copy yet” или “last copy 3 days ago”. Пометка в строке: “no copy anywhere” (копии нет ни в одном назначении), “no fresh copy anywhere” (есть, но все устарели) или “no fresh copy on “NAS””; если причина у всех таких назначений одна, она добавляется через “ · ”. Полный список «назначение: причина» — в подсказке и в тексте статуса. Источник, который ещё ни разу не запускался и ничего не доставлял, — нейтральный (“Never run”, серый значок), не зелёный. Выключенный источник нейтрален, источник без назначений — “No destination chosen”. Пока источник выполняется или стоит в очереди, свежая копия от него не требуется (5.6). Новых напоминаний и уведомлений это правило не добавляет; пока статус не спокойный, планировщик, как и раньше, проверяет раз в час.

**Один снимок.** Всё, что говорит о состоянии бэкапов — значок строки, значки назначений в строке, заголовок окна, строки меню, “All good” в меню и значок в menu bar, — строится из одного снимка последней проверки (`StatusSnapshot`), поэтому они не расходятся: общий итог — худшее из итога проверки и строк меню; “All good” и спокойный значок — только когда итог спокойный и строк нет. До первой проверки снимка нет: ничто не зелёное, значки назначений серые без метки (“not checked yet”). Назначение, которое не использует ни один включённый источник, частью здоровья бэкапов не является: его проблема (не тот диск, не APFS, нет папки) видна в его настройках, но строкой меню не показывается, итог не портит, а в строке назначений внизу обзора не выделяется цветом. Источник, который выполняется или стоит в очереди, сохраняет доказанное проверкой: его прежние проблемы не показываются и не считаются (5.6), но устаревшая копия остаётся оранжевой на значке назначения, а не становится зелёной.

Значок в menu bar цветной: жёлтый — нужно действие, красный — ошибка, обычный (белый/чёрный по теме) — всё в порядке. Меню по клику, сверху вниз: “Open window”; блок состояния без общего заголовка — по одной строке на проблему: значок состояния (красный — ошибка, оранжевый — нужно действие), значок источника или назначения, имя и короткая причина (“time to export”, “2 files · 23 GB” с кнопкой “Pick up”); ошибки идут первыми; у источника одна строка, даже если проблем несколько. Если спокойный статус доказан (выше) и строк нет — “All good · last backup N ago”; до первой проверки после запуска не показывается ничего успокаивающего (значок — как при работе, заголовок окна — “Checking…”). Клик в любое место блока открывает окно на “Overview”, даже когда действий не нужно; “Back up everything again”; “Quit”. Ошибка в меню показывается одной короткой фразой (полный текст — в окне). Во время работы первой идёт строка выполняющегося источника: “GitHub · 9 of 79 · owner/repo · 4 min”. “Launch at login” живёт в разделе окна “Settings”.

### 5.6. Окно

- **Обзор** — один компактный список, строка на источник. В строке видно только: значок состояния, название, короткая пометка (появляется, только когда что-то не так или идёт работа), давность последнего бэкапа, когда следующий (“→ in 17 h”, “→ due”, “→ manual” у источников “Manual only”, “→ waiting”, пока источник ждёт файл или устройство) и значки назначений. Точное время следующего бэкапа — при наведении и в настройках источника строкой “Next backup”. Подробности — при наведении. В шапке — “Refresh” (тот же `tick()`, что идёт сам по таймеру и событиям: докопировать недостающее и запустить то, чему пора; лишних бэкапов не делает) и “Back up everything again” (собрать всё заново и записать на все подключённые диски); то же есть в меню строки меню. Запуски доступны и во время идущего бэкапа — встают в очередь. Порядок строк выбирается в шапке: “As in settings” (порядок из “Sources”) или “By next backup” (ближайший и просроченный выше; без расписания и выключенные — внизу в порядке настроек); выбор запоминается. Кнопки строки появляются при наведении прямо в строке, пометка на это время укорачивается; обрезанная пометка целиком видна в подсказке. Источник, который ждёт своей очереди, помечен песочными часами и “queued” — в том числе сразу после “Run” или “Back up everything again”, нажатых, пока идёт другой бэкап (помечаются те, что пойдут в работу, а не будут ждать файл или устройство). Проверка, вставшая в очередь за идущим бэкапом (например, после сохранения настроек), сразу помечает то, что сделает наверняка: источники, которым пора по расписанию, и долги перед доступной локальной папкой или диском, которые есть чем закрыть и которые пора повторять. Пока идёт шаг без своего прогресса, пометка говорит, что он делает: “copying files…” или “running the command…”.
- **Подсказки и кнопки во всём приложении.** Открытая подсказка следит за своим текстом (идущее время обновляется). Подсказка к идущему бэкапу сравнивает его с прошлым таким же: копирование с другого диска — с прошлым копированием, сбор — с прошлым плановым или ручным сбором; запись пакета после шагов человека для сравнения не годится; не с чем сравнить — прогноза нет. Подсказка всплывает через полсекунды (следующая — сразу), пропускает мышь насквозь и исчезает при уходе курсора, клике, прокрутке или нажатии клавиши: курсор и клик под ней работают. Кнопка нажимается всей своей площадью, под курсором подсвечивается, при нажатии темнеет, выключенная — приглушена и без руки-курсора. Пункты меню в строке меню — строки во всю ширину с подсветкой; блок состояния в меню целиком открывает обзор.
  - Шапка: общий итог (“All good” — только при спокойном статусе 5.5, “Needs your action”, “N errors”; до первой проверки — “Checking…”), имя источника, который идёт сейчас, кнопка «запустить всё».
  - Пометка во время работы: “queued”, “preparing the copy…”, “copying to “destination name”…”. Если команда источника что-то печатает в stdout, последняя непустая строка показывается как ход работы: “preparing the copy · 54 of 79 · owner/repo” (шаблон GitHub печатает номер и имя репозитория). Вместо давности на время работы показывается, сколько уже идёт запуск; при наведении — сколько занял прошлый успешный запуск.
  - Пока источник в очереди или выполняется, его прежние проблемы (ошибка прошлого запуска, просрочка) не показываются и не считаются — ни в заголовке, ни в списке, ни в menu bar. Если других проблем нет, заголовок на это время — “Backing up”. Лучше доказанного он при этом не выглядит: значок строки не зелёный без доказанной свежести, а значки назначений показывают то, что доказала последняя проверка (5.5, «Один снимок»).
  - Текст ошибки в строке — кнопка: открывает окно с полным текстом (прокрутка, выделение, “Copy”). При наведении показывается только подсказка, а не сам текст. То же окно доступно из «⋯ → Показать ошибку». В “History” у запуска с ошибкой полный текст выделяется и копируется кнопкой.
  - Значок состояния в строке: зелёная галочка — только у источника со свежей копией в каждом назначении (5.5); оранжевый — нужно действие или нет свежей копии; красный — ошибка; серый пунктирный круг — ещё ни разу не запускался или свежесть пока не подтверждена.
  - Пометка при проблеме: “no copy anywhere · formatted as exFAT, needs APFS”, “no fresh copy on “NAS” · unavailable” (5.5); у давно не бэкапившегося источника причина идёт вместе с давностью и не прячется за красным: “no copy anywhere · formatted as exFAT, needs APFS · no backup for a long time”, начало текста ошибки (для упавшей команды — последняя непустая строка её вывода, в ней обычно причина), “N files · size” с кнопкой “Pick up”, “time to export”, у доставки с предупреждением — начало предупреждения (“Could not clean up old copies”). Полный текст — при наведении.
  - У источника из нескольких шагов пометки о самом запуске (пора сделать экспорт, пора подключить, найденные файлы, ждёт файл, ждёт подключения, ошибка шага) начинаются с положения: “step 1 of 2 · time to export”, “step 2 of 3 · waiting for a file”, во время команды — “step 2 of 2 · downloaded 3 of 5”, при ошибке — “step 2 of 2 · <начало текста ошибки>”; остальные (“no destination chosen”, ошибка доставки) — без положения. Те же тексты — в строке меню. Кнопки при наведении описаны ниже.
  - Значок назначения — диск или облако с меткой, из того же снимка проверки, что и всё остальное (5.5), а не из истории прогонов: зелёная галочка — проверка доказала, что копия источника там есть и она в ритме назначения; оранжевый восклицательный знак — копия есть, но старше ритма назначения (5.5), при наведении “this copy is older than expected”; оранжевые часы — ещё не доставлена, назначение недоступно; красный крест — запись упала; синий пульсирующий — записывается сейчас; серый без метки — копий ещё не было, либо свежесть не проверена (до первой проверки, выключенный источник: “not checked yet”). При наведении — имя назначения и время доставки.
  - Давность последнего бэкапа — это возраст самой свежей копии источника, которая по записям есть хотя бы в одном его назначении (`deliveredAt`), включая догон и восстановление пропавшей копии; копия, пропажу которой обнаружила сверка (5.3.1), и копии в назначениях, убранных из источника, не считаются; расписание при этом отсчитывается отдельно, от последнего планового прогона. Запуск, который не доставил копию ни в одно назначение (диск отключён, запись упала), давностью не считается: у такого источника давность “—”, и “last backup …” в меню строки меню его не учитывает. Для `state.json` из старых версий без `deliveredAt` даты копий один раз восстанавливаются из истории при чтении состояния (6).
  - При наведении на давность — точное время последнего и следующего бэкапа и размер копии. При наведении на строку — кнопки-значки без меню «⋯»: “Run” (у упавшего шага — “Retry step”), “Start over” (у цепочки, которая в процессе), “Instructions” (если она есть), “Show original in Finder” (у папки — открывает её в Finder), “Open copy” (самая свежая доставленная копия в Finder; при нескольких назначениях — выбор из списка, копия в облаке видна, но неактивна; копия на диске, который не подключён или не подтверждён, — тоже, 4.2.1), “Edit”. Кнопки, которые ничего не сделают, не показываются. Клик по свободному месту строки открывает настройки источника; полный текст ошибки открывается кликом по самой пометке.
  - Внизу — строка назначений; текстом выделяется только требующее действия (“time to connect”, “unavailable”). Назначение, которое сейчас не подключено, приглушено; меток в углу значка в этой строке нет — состояние видно по цвету и тексту. Каждое назначение — кнопка: подключённую папку или диск открывает в Finder, а облако и неподключённый диск — в настройках назначения. Рядом с именем — сколько занимают копии (у отключённого диска — на момент последнего подключения; считается в фоне между бэкапами: сразу после бэкапа и как только диск подключили, а при прочих обновлениях экрана — не чаще раза в минуту). Под строкой — “Backups need about N of free space on the laptop · M free”: бэкапы идут по одному, поэтому N — самый большой из последних бэкапов включённых источников, которые собираются во временную папку (папка из одного шага копируется напрямую и не считается), плюс пакеты, которые ждут записи на отключённый диск (пакет самого большого источника — это его же последний бэкап и второй раз не считается; если размер последнего бэкапа неизвестен, пакет считается); если свободно меньше N — строка оранжевая с предупреждением. Подробности — в подсказке.
- **Источники** — два столбца в стиле обзора: слева список (значок, имя, “Add”: шаблоны и “Empty — start with”: “Folder”, “Command”, “File you export yourself”, “Folder on a connected device” — последний сразу создаёт два шага; источники переставляются перетаскиванием: брошенный встаёт на место того, на который его бросили, на “Add” — в конец; полоска показывает, куда встанет; этот порядок — порядок источников везде: в обзоре, меню и настройках), справа: шапка (значок — клик выбирает картинку, имя, выключатель, «⋯» с “Remove icon” и удалением), под ней описание, затем блоки: выделенный цветом “How often and where” (расписание, “Next backup”, назначения-чипы, выключатель “Save space” — 4.3.1), “What to do” — карточки шагов по порядку (у источника из одного шага — без номера и стрелок; вид шага, название и поля вида; “Add step”, переставить, удалить; текущий шаг запуска подсвечен), “More” (свёрнутые “Keep copies” и “Instructions: one-time setup”). “Keep copies” — четыре строки, точно описывающие правило 4.4 (считаются периоды, в которые был бэкап, а не календарное время): “Keep one copy per day for the last [7] days you backed up”, то же для week, month, year; под ними “Older copies are deleted. The newest copy is always kept.” (если все нули — “Only the newest copy is kept.”). Числа меняются прямо в строках; строка с нулём приглушена и подписана “not used”. Свёрнутая строка показывает самый длинный этап (“last 12 months you backed up”). Там же кнопка “Show copies by date…”. Значок источника показывается и в обзоре.
- **Назначения** — те же два столбца. В списке и шапке значок с меткой состояния (на связи, не подключено, пора подключить, недоступно, не тот или неопознанный диск, папки нет), подробности при наведении. Карточка настроек: папка или облако (список remote из `rclone listremotes`), режим подключения, срок напоминания. Ниже “Copies”: занятое место и строки по источникам (число копий, возраст последней), раскрываются в список дат. Для папки на внешнем диске — строка “Disk” с запомненным диском и кнопкой “Read from connected disk”, под именем назначения — пояснение и кнопка “This is my <назначение>”, если подключён не тот или неподтверждённый диск (4.2.1). Для локальных назначений при наведении на копию — “Show in Finder”; для облака показывается имя папки снапшота (универсальной ссылки «открыть в облаке» у rclone нет).
- Планка “Cancel / Save” появляется только при несохранённых изменениях (или при добавлении); в ней же показывается, чего не хватает для сохранения. Если записать настройки не удалось (например, `config.json` повреждён), показывается ошибка, а правки остаются несохранёнными: планка не исчезает, новый источник или назначение не считается добавленным, удаление не происходит. После сохранения редактор показывает источник таким, каким он записан (с папкой копий, выбранной по имени), поэтому “Show copies by date…” у только что добавленного источника смотрит в его папку.
- Размеры округляются до показа, и единица выбирается по округлённому числу: 999 950 байт — “1 MB”, а не “1000 KB”.
- Второй запуск приложения, пока первое работает, сразу завершается и ничего не трогает: не чистит `staging/` (там может идти бэкап первого), не создаёт настройки, не убирает значки и не открывает окно. Второй запуск определяется по другим процессам с тем же bundle id (свой процесс не в счёт), поэтому он распознаётся и при запуске бинарника напрямую, мимо LaunchServices.
- Окно запоминает последний открытый раздел и выбранный элемент. При первом запуске (нет ни одного назначения) окно открывается само, дальше приложение живёт в menu bar.
- **История** — журнал прогонов с фильтром по источнику и результату.

### 5.7. Шаблоны

Шаблон — JSON-файл с предзаполненными полями источника (шаги, расписание, хранение, описание, инструкция). Встроенные шаблоны копируются в папку данных при первом запуске. Свой шаблон добавляется файлом в эту папку.

## 6. Данные приложения

Папка данных `~/BackupEverything/` (бэкапится источником “Backup Everything settings”):

```
config.json            источники, назначения (у папки на внешнем диске — её диск, `disk`) и имена папок удалённых источников (`retiredSlugs`)
state.json             последние сборы, долги, отметки подхвата, положение в цепочках шагов, последняя доставленная копия в каждой паре «источник, назначение» (`lastDelivered`), момент её сбора (`deliveredAt`), с какого момента пара ждёт копию (`expectedSince`) и место назначения, у которого собраны факты (`destinations.<id>.location`)
history/YYYY-MM.jsonl  прогоны, одна строка — один прогон
templates/*.json       шаблоны источников
icons/*.png            значки источников
```

Рабочая папка `~/Library/Application Support/BackupEverything/` (не бэкапится):

```
pending/<sourceId>/<timestamp>/   подхваченные, но не доставленные пакеты
chains/<sourceId>/                рабочие папки цепочки шагов: input/, output/, scratch/; process.json — идущая команда шага; pickup.json — что взял шаг “Get a file from you”, пока запуск не перешёл дальше
staging/                          временные выходные папки команд; <папка запуска>/process.json — идущая команда; при запуске приложения оставшиеся команды останавливаются, затем содержимое input/ и output/ каждой папки запуска уходит в Корзину, остальное удаляется
```

- Запись файлов состояния атомарная (временный файл и переименование).
- Прогон дописывается в конец `history/YYYY-MM.jsonl`. Если прошлая запись оборвалась на середине строки (приложение упало), новая начинается с новой строки: оборванная пропускается при чтении, новая не теряется. Месяц читается построчно как байты: строка, оборванная посреди многобайтной буквы (кириллица), — не UTF-8 и пропускается одна, а не скрывает весь месяц. Поле прогона `deliversAnOlderCopy` добавлено без смены формата (5.3).
- Рабочие папки удалённых источников (`chains/<sourceId>/`, `pending/<sourceId>/`) при следующем `tick()` уходят в Корзину.
- В рабочих папках лежат копии с замками, правами только для чтения и списками доступа «запретить удаление» оригиналов. Когда приложение убирает что-то из `pending`, `chains` или `staging`, такие препятствия снимаются (без перехода по ссылкам): элемент сначала отправляется в Корзину как есть, и только если не вышло — разблокируется целиком и отправляется снова; удаляемое безвозвратно разблокируется всегда. Файл, у которого есть другие имена (жёсткая ссылка, например `ln` или `cp -al` на файл человека в выходной папке команды), не меняется никогда — ни замок, ни права, ни список доступа: это тот же файл, что у человека. Убирается только его имя в рабочей папке, при этом ничего не теряется. Если сам файл защищён от удаления (замок или «запретить удаление»), уборка падает с ошибкой ““…” is another name (a hard link) of a file elsewhere, and that file is protected from deletion …”, и файл человека остаётся защищённым. В назначениях копии сохраняют права оригиналов.
- Файлы версионируются полем `schemaVersion`. Поле `retiredSlugs` в `config.json` добавлено без смены версии: файл без него читается как «удалённых источников нет». Поле `disk` назначения тоже: назначение без него — «диск не подтверждён». Поле `deliveredAt` в `state.json` добавлено без смены версии: при чтении состояния без него даты копий восстанавливаются из истории — прогон, доставивший копию, записанную в `lastDelivered`, иначе дата из имени этой копии (не позже последнего успешного сбора). Дата — факт о копии, которая есть сейчас, поэтому она восстанавливается только для пары, у которой копия названа в `lastDelivered` и нет открытого долга; пара без имени (копии до `lastDelivered`, копия, пропажу которой нашла сверка) из истории даты не получает — её заводит сверка, найдя копию (5.3.1). Поля `expectedSince` и `location` добавлены без смены версии: при первом чтении нынешние пары считаются ожидаемыми с создания источника, а нынешнее место назначения принимается как место его фактов. Восстановленное сохраняется при следующей записи состояния. Сверка (5.3.1), обнаружив пропажу копии, забывает и имя, и дату.
- Секретов в папке данных нет.

## 7. Архитектура

Два модуля:

- **`BackupCore`** — Swift Package без зависимостей от UI. Вся логика и все тесты.
- **`BackupEverythingApp`** — SwiftUI: `MenuBarExtra`, окно, уведомления, автозапуск (`SMAppService`). Читает наблюдаемое состояние ядра и вызывает его команды.

Приложение не в песочнице (запуск команд и доступ к произвольным папкам), распространяется локальной сборкой.

Компоненты ядра:

| Компонент | Ответственность | Зависит от |
|---|---|---|
| `SourceProvider` (протокол) и `FolderSource` (одна папка), `StepsSource` (автоматические шаги), `PendingSource` (результат из `pending`) | Собрать содержимое снапшота (`Payload`) и убрать за собой после прогона | `ProcessRunner`, `ManualExportInbox` |
| `ManualExportInbox` | Поиск файлов шага “Get a file from you”, хранение недоставленного пакета в `pending` | — |
| `StepExecutor` | Выполнить автоматический шаг (папку или команду) в рабочих папках запуска | `ProcessRunner` |
| `StepChainRunner` | Сделать один переход запуска источника с шагом человека: принять файл (`FilePickup`: всё или ничего, отмена незаписанного подхвата), дождаться устройства, выполнить автоматический шаг или собрать результат в `pending`. `BackupCoordinator` вызывает его в цикле и сохраняет состояние после каждого перехода | `ManualExportInbox`, `StepExecutor` |
| `DestinationStore` (протокол) и `LocalFolderDestination`, `RcloneDestination` | `isAvailable`, `write(payload)`, `listSnapshots`, `removeIncomplete`, `delete(snapshot)`, `usedBytes` | `ProcessRunner` |
| `PayloadWalker`, `PayloadCopier`, `WrittenCopy` | Список содержимого `Payload` (ошибка на нечитаемом и на имени не в UTF-8), копия ровно этого списка движком Apple (`copyfile`) и проверка копии по списку: шаг “Copy folder” и запись локального снапшота | — |
| `SnapshotWriter`, `SpaceSaving`, `FileCloning` (`APFSCloning`), `DestinationUsage` | Запись локального снапшота: полная копия, манифест по ней, затем клоны файлов, не изменившихся с предыдущей копии (4.3.1); учёт занятого места | — |
| `FolderRemoval`, `VolumeMounts`, `DiskFormat` | Удаление снапшота вместе с замками, правами и списками доступа; проверка, что том в `/Volumes` смонтирован; файловая система диска папки назначения (только APFS) | — |
| `SystemDisks`, `DiskArbitrationVolumes`, `DiskCheck` | На каком диске лежит папка (системный, внешний не подключён, внешний с его Volume UUID из Disk Arbitration, внешний неопознанный) и тот ли это диск, что подтверждён для назначения (4.2.1) | — |
| `RetentionPolicy` | Чистая функция: список снапшотов и правило → что оставить | — |
| `BackupEngine` | Один прогон: сбор, доставка, чистка; возвращает запись прогона | провайдеры, `RetentionPolicy` |
| `StateReducer` | Применить запись прогона к состоянию: долги, сроки, ошибки | — |
| `SchedulePlanner` | Чистые расчёты: что пора запускать, какие долги повторять, когда проснуться | — |
| `BackupCoordinator` (actor) | `tick()`: догон, подхват, плановые прогоны, напоминания; строго по одному | всё перечисленное, `TimeSource` |
| `FolderWatcher` | События файловой системы для папок шагов “Get a file from you” (FSEvents) | — |
| `Store` | Чтение и атомарная запись `config`, `state`, `history`, `templates` | — |
| `StatusReporter`, `ReminderPlanner` | Сводный статус для UI и напоминания раз в сутки | `SchedulePlanner` |

Новые виды шагов добавляются в `StepKind`, `StepExecutor`/`StepChainRunner` и форму шага; новые типы назначений — реализацией протокола и регистрацией в фабрике; остальной код о конкретных типах не знает. Шифрование позже добавляется как обёртка над `DestinationStore` (или через rclone crypt) без изменений движка.

Запуск процессов и время спрятаны за протоколами `ProcessRunner` и `TimeSource`. Файловые операции не абстрагируются: тесты работают с настоящими временными папками, это надёжнее поддельной файловой системы. Состояние с конкурентным доступом изолировано актором `BackupCoordinator`.

Реализация идёт двумя планами. Первый — `BackupCore` целиком, без системных событий. Второй — приложение: таймер до ближайшего срока, события пробуждения и монтирования, `FolderWatcher`, уведомления, автозапуск и UI; все они вызывают `BackupCoordinator.tick()`.

## 8. Тестирование

Разработка через TDD.

- `RetentionPolicy` — табличные тесты: пропуски, границы недель и месяцев, нулевые правила, единственный снапшот.
- `BackupEngine` — тесты на фейковых провайдерах: успех, сбой одного назначения, недоступное назначение и долг, догон, порядок «запись, затем чистка недописанных, затем GFS», без чистки при упавшей записи.
- Недописанные снапшоты — в Корзину уходят только папки с меткой `_unfinished` и без манифеста; папка без метки и посторонние папки не трогаются; повтор под тем же именем; мешающая чужая папка — для локальной папки и облака.
- Имена снапшотов при переводе часов, принадлежность копий источнику по манифесту, имена папок удалённых источников, пересечение масок.
- `SchedulePlanner` и `BackupCoordinator` — тесты с управляемым временем: срок, повтор через час, догон при возврате диска, одновременные `tick()`.
- `ManualExportSource` — автоподхват в режиме `single`, подхват по подтверждению в режиме `multiple`, незавершённые загрузки, старые файлы, замена пакета в `pending`.
- Долги и `expectedEvery` — статус и напоминания до и после истечения интервала, один снапшот при догоне.
- Свежесть копий (5.5) — табличный тест статуса источника: свежие копии везде — зелёный; устаревшая копия в одном назначении “Always connected” — жёлтый с назначением; оба назначения отказали (не APFS) — “no copy anywhere”; диск “up to 30 days” с копией 10 дней — зелёный, после срока — жёлтый; запуски без единой доставки — не зелёный; упавший запуск — красный; просрочка по возрасту доставленной копии при недавнем запуске — красный; выключенный и ни разу не запускавшийся — нейтральные. Общий статус, заголовок, меню и значок в строке меню не говорят “All good”, пока хоть один источник без свежей копии.
- `CommandSource` — код возврата, таймаут, пустой результат (фейковый `ProcessRunner`).
- `StepChainRunner` и цепочки в `BackupCoordinator` — ручной шаг ждёт и принимает файл, `includeInCopy`, передача файлов команде, остановка на ошибке без автоповтора, “Retry step”, “Start over”, перезапуск новым файлом первого шага, продолжение после перезапуска приложения (повтор прерванного шага с чистого места, возврат файлов незаписанного подхвата, остановка оставшейся от прошлого запуска команды, команда, остановленная выходом из приложения, не записывается), доставка и догон через `pending`; шаг “Copy folder” не пишет поверх того, что положил предыдущий шаг; имя не в UTF-8 в выходной папке (образ FAT16 `TEST-BE-…`) — ошибка шага.
- Команда шаблона Claude — на временной папке вместо «Загрузок» и с подменой `open`: уже скачанные архивы не открываются повторно, устаревший одноимённый файл останавливает шаг до открытия ссылок, недостающие перечислены в ошибке.
- `Store` — атомарность записи, чтение повреждённого файла, миграция `schemaVersion`.
- Экономия места (4.3.1) — на временной папке APFS: каждый снапшот полный и совпадает с источником; клонами становятся только файлы с тем же путём, содержимым и метаданными (общий clone id, ни одного собственного байта); перемещённый файл, файл с другими тегами, правами или флагами, с замком и с запретом удаления пишутся целиком; правка клона не трогает оригинал; правленый руками, недописанный, чужой, более старый и старого формата снапшот не служат оригиналом; сбой клонирования и клон не того размера оставляют полный файл без временных остатков; файл предыдущей копии, изменённый на месте с тем же размером и датой, не клонируется; клон, который не удалить, оставляет копию недописанной с путём в ошибке; папки сохраняют даты; том без клонов; удаление старого снапшота; учёт места.
- Сохранность данных в локальном назначении — замки Finder, папки только для чтения и со списком доступа «запретить удаление», нечитаемые папки источника и назначения, ссылка вместо пути источника, служебные имена на верхнем уровне и глубже, прерванное удаление, оставшаяся папка в `/Volumes` (и путь к ней через ссылку или другое написание), пустой или ведущий наружу `slug`.
- Сжатые APFS файлы — на настоящем сжатом файле (`ditto --hfsCompression`, флаг проверяется): каждый снапшот и догон на другой диск целые и сжатые; обычный файл не становится клоном сжатого; испорченный прежней версией снапшот не служит оригиналом.
- Рабочие папки с замками, папками только для чтения и «запретить удаление»: доставка пакета, новый пакет на месте недоставленного, отмена, отключение устройства посреди копирования, упавшая команда, перенёсшая оригинал. Исчезнувшие во время обхода и копирования файлы и папки.
- Чужие файловые системы — на образах дисков, подключённых только на время теста (`hdiutil`, без показа в Finder, имена `TEST-BE-…`): назначение на exFAT, FAT32 и Mac OS Extended отказывает во всём с текстом про APFS и ничего не пишет; exFAT и FAT32 как источник со спутниками `._x` (атрибуты переезжают, спутник отдельно не копируется, `._` без пары копируется); на APFS файлы `._x` рядом с `x` (и с содержимым в формате AppleDouble, и с обычным) копируются как файлы, удаляются и учитываются в занятом месте; имя с одиночным суррогатом на FAT16 (не UTF-8): сбор, удаление и подсчёт места; отключение диска источника посреди копирования (APFS), в том числе диска, подключённого внутри папки источника, переименование и подмена папки источника.
- Копирование и проверка копии — исключённые файлы и папки не попадают в копию; ссылки в папках только для чтения и с замком приходят, папки со ссылками сохраняют даты; папка копии сохраняет свои права; удалённый из копии, укороченный файл, подменённая ссылка и папка, ставшая файлом, оставляют копию недописанной с путём в ошибке; файл, изменившийся во время копирования, принимается; часть файла, оригинал которого исчез, убирается из копии и манифеста (с замком тоже), а если убрать нельзя (папка только для чтения) — ошибка; у оригинала на отключённом диске или без доступа — ошибка об этом; файл, пропавший из копии до составления манифеста, и файл копии, который не прочитать для манифеста, — ошибка с путём. Копирование ничего не перезаписывает: файл, папка и ссылка, уже лежащие в папке копии (и подложенные во время копирования), остаются как были, ссылка не используется для записи, ошибка называет путь; имена, отличающиеся только регистром, с регистрозависимого APFS (образ `TEST-BE-…`) на верхнем уровне, глубже и у папок — ошибка; два элемента списка, ставшие одним элементом копии, — ошибка проверки; исключённое имя не трогает папку, которая уже была на месте.
- Жёсткие ссылки на файлы человека в рабочих папках: уборка не трогает их замок, права и список доступа.
- Выход по сигналу останавливает команды; команда источника без ручных шагов, оставшаяся от убитого приложения, останавливается при следующем запуске.
- Диск назначения (4.2.1) — с подменой macOS (`DiskLocating`): подтверждённый, неподтверждённый, другой, без UUID, неопознанный, системный диск, не подключённый подтверждённый диск с оставшейся папкой; отказ хранилища во всех операциях; “Open copy” и кнопки подтверждения. На настоящих образах APFS, exFAT и FAT32 с выдуманными именами `TEST-BE-…`, смонтированных в папку теста вместо `/Volumes`: UUID читается и не меняется после трёх переподключений; на APFS и exFAT он совпадает с тем, что сообщает Foundation (прежние привязки); неопознанный диск не совпадает с привязкой без UUID; на APFS: неподтверждённый диск ничего не получает и `config.json` сам не меняется; после подтверждения копии идут, тот же образ после переподключения принимается; другой образ (или «переформатированный» диск) с тем же именем ничего не получает и ничего не теряет, пока его не подтвердили. Имена настоящих дисков в тестах не используются.
- Интеграционные: `LocalFolderDestination` на временной папке; `RcloneDestination` на rclone-бэкенде `local`, без сети.
- UI проверяется запуском приложения вручную.
